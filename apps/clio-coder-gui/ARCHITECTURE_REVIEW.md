## 2. Verdict in one paragraph

Accept the shape of Astra's proposal: an app-owned, transport-independent service layer under `apps/`, sessions in supervised `clio-coder acp` children, REST for commands and queries, SSE for events, TypeBox contracts, React plus Vite, Deno retired, toolchain as the first vertical. Amend four things with evidence. Use Hono on `@hono/node-server` rather than Fastify. The comparison in section 6.3 comes out close on the glue code the app would own either way; what tips it is that the app needs its own route table anyway to keep a typed client from drifting, which leaves Fastify's validation and OpenAPI plugins with little left to remove, while Fastify's dependency tree is the part of the ecosystem that is hardest to carry into the root `dist/` at v0.5.0. Put every source-import adapter in domain worker threads rather than the HTTP process, because the seams the app wants are synchronous (`spawnSync` version probes with a 2 s timeout, synchronous SQLite with a 5 s busy timeout, synchronous archive unpacking). Drop the workbench's snapshot-window artifact allowlist and the host-side-only payload policy; they were the right answer for a browser the host distrusted, and the wrong answer for a loopback app with a per-launch token whose purpose is a trace explorer richer than the eight-run summary. Do not generate an HTTP client; the client imports the contract types from the same workspace package. Reject one thing: hosting many workspaces inside one orchestrator process. The ACP server is one session per process pinned to one canonical cwd, the orchestrator boots against `process.cwd()`, and the shared bus and Pi registry are process globals. That stays a child-process boundary.

## 5. Advisor findings raised mid-review, and where they land

1. **Synchronous seams (`spawnSync` probes, synchronous SQLite with a 5 s busy timeout, synchronous archive work) must stay off the HTTP and session event path.** Confirmed in `version.ts`, `trace-store.ts`, `archive.ts`. Resolved by the two domain workers (section 7.2) with bounded queues and per-call deadlines; the HTTP process imports no `src/**` module except the asynchronous or trivial ones it needs for session children and identity (`src/engine/acp/transport.ts` and its errors and types, `src/core/xdg.ts`, `src/core/package-root.ts`, `src/domains/lifecycle/version.ts`). A boundary test enforces this.
2. **Root `package.json` exports no runtime service API; source-import adapters must state checkout coupling and their v0.5.0 packaged resolution.** Confirmed. Section 8 classifies every seam, and the v0.5.0 resolution is a root tsup entry that bundles the server beside the CLI, not a new public export.
3. **`core/package-root.ts` caches the nearest `package.json` above `import.meta.url`, so bundling Clio source underneath the app misidentifies the root.** Confirmed and important. In the foundation the server runs from source through `tsx`, so `import.meta.url` stays under `<repo>/src/` and the walk finds the repo root. The app never bundles `src/**` into its own `dist/`. At v0.5.0 the root build emits `dist/web/server.js`, whose walk finds the package root. A packaging rehearsal slice pins `CLIO_CODER_PACKAGE_ROOT` explicitly to prove the failure mode and the fix.
4. **`TraceReader.runs` caps at 500 with no cursor; specify real full-history pagination.** Confirmed. Section 7.5 specifies keyset pagination over `(started_at, run_id)` executed as app-owned parameterised SQL through the public `TraceReader.db` handle against the documented schema v1, in the worker, with a proposed root seam `TraceReader.runsPage` at v0.5.0.
5. **Do not delete `apps/trace-viewer` while `src/cli/trace.ts` and root CI reference it.** Agreed. Retirement is root integration slice R2, after the web trace explorer covers the matrix in `SPRINT.md` section 7.
6. **Desktop visibility after install needs a platform-specific plan; ordinary CLI invocation must not auto-start a daemon.** Section 9. Explicit web launch actions start the foreground server, including the docs navigation command after R3. Linux freedesktop launch is the initial verification target; the new launcher has not been implemented or measured. macOS and Windows browser launch remains unverified until someone runs it.

## 6. The three real architecture choices

### 6.1 Where live sessions run

| Option | Description | Verdict |
| --- | --- | --- |
| A1 | One supervised `clio-coder acp --cwd <root>` child per open session, driven through `createStdioTransport` | **Recommended** |
| A2 | Boot the orchestrator in the web server process with an injected `BootOptions.acp.transport` (in-memory JSON-RPC pair), one workspace per server | Bounded experiment only (E3) |
| A3 | A new multi-session `clio-coder serve` daemon inside the root harness | Rejected for this milestone |

A1 keeps the CLI, TUI, and ACP untouched, reuses the one hardened client transport in the tree, and matches what the workbench already proved works. Its costs are real: each child boots the full orchestrator graph, so memory per open session is the price of isolation, and every management fact the session exposes (safe settings, targets, session list) comes through the ACP extension methods rather than direct calls. A2 would remove the process hop for a desktop-per-project launcher but inherits every process-global in the orchestrator, so it can only ever host one workspace and would make the web server itself workspace-bound. A3 is the only path to a true multi-workspace daemon and it is root harness work of a different scale (process-global bus, Pi registry, `process.cwd()` coupling in settings and ledgers); it belongs to a later milestone if ever.

Consequences of A1: maintenance is one supervisor module plus a projection; the frontend sees sessions as resources with a lifecycle independent of the browser; session semantics are exactly ACP v1 plus the `clio-coder/` extensions, no more; no new dependencies; packaging is unaffected because the child is the installed `clio-coder`; v0.5.0 integration needs nothing from the root beyond the existing command.

### 6.2 How management reads and mutations reach Clio

| Option | Description | Verdict |
| --- | --- | --- |
| B1 | Fixed-argv CLI children for every read and write (the workbench model) | Rejected for reads |
| B2 | Direct source imports for everything, including writes | Rejected for writes |
| B3 | Direct source imports for reads, executed in a domain worker; CLI children with fixed argv for mutations whose admission logic lives in CLI commands; ACP extension methods for facts a live session owns | **Recommended** |

B1 is why the workbench carries 5,153 lines of re-validation: a subprocess boundary turns typed domain values into untyped JSON that has to be re-checked key by key. B2 would make the app re-implement admission rules that `targets`, `library`, `extensions`, `evidence build`, and `fleet run` own today, which is the second harness the brief forbids. B3 keeps types flowing from `src/**` for reads (the TypeBox schema at the API edge is the only validation layer), keeps mutations behind the boundaries that already guard them, and keeps blocking work off the event loop.

Consequences: maintenance shifts from thirteen bespoke inspectors to one worker RPC plus per-area adapters that are mostly projection; the frontend gets richer reads than the CLI summaries allowed; session semantics are untouched; dependencies are unchanged; packaging at v0.5.0 bundles the adapters into the same `dist/web/server.js` chunk graph; the one root cost is exporting a handful of currently unexported snapshot builders when a session decides to reuse one rather than re-project from the domain seam underneath it.

### 6.3 The HTTP layer

The workload first, because it decides this: about forty loopback routes, JSON in and out, one operator, three or four SSE streams, static assets, bearer-token auth, problem responses, TypeBox schemas that must also produce an OpenAPI document at v0.5.0, and a browser client whose verb, path, body, and result types must not drift from the server.

That last requirement is the pivot. Importing `Static<T>` from a shared schema types a body; it does not bind a verb and a path to that body and its result. What binds them is a **route table**: one `defineRoute({ method, path, params, query, body, response, summary })` per endpoint in `contracts/routes.ts`, with TypeBox schemas as the only schema language. Three consumers read that table and nothing else defines an endpoint: the server adapter registers handlers from it (handler input and output types come from the route object), the OpenAPI script emits `openapi.json` from it (TypeBox is JSON Schema, so the emitter is assembly, not translation), and the client `call(route, input)` is typed from it. Remove a route from the table and the client stops compiling; change a body schema and both sides change together. A test asserts that every registered handler corresponds to a table entry and every table entry has a handler. Codegen is unnecessary because the table is already the code.

With the table in place, here is what each framework option still removes from the app, and what it adds.

| Owned glue, rough total | ~290 lines + 4 packages | ~340 lines + 2 packages |

Corrected packaging fact: root `tsup.config.ts` bundles a selected pure-JS tail into `dist/` and externalises the declared `dependencies`; it does not prohibit a new runtime dependency (there are seven today). Either framework could ship as a runtime dependency at v0.5.0. The difference is what that costs: Hono is two zero-dependency ESM packages that bundle or externalise trivially; Fastify's tree includes `pino` (worker-thread transports resolved by file path) and ajv, which are the parts of the ecosystem that bundle worst and would most likely have to ship external, adding their whole tree to every Clio install for a loopback app with one operator.

Decision: Hono. The app owns roughly fifty more lines (the OpenAPI emitter) and gives up schema-driven serialisation, which was never the field filter anyway: every resource has an explicit public projection function in `server/services/**`, and contract tests check that projections satisfy their response schema. The glue estimates above are unmeasured hypotheses; E4 measures them. In return the server adds two zero-dependency packages, SSE is built in, and the table, not the framework, is what keeps the client honest. The service layer and the table keep a swap to Fastify confined to `server/http/**` if a concrete need appears (E4).

Version policy for all of the above: the versions in section 3 are what the registry served on 2026-09-11. The first implementation slice pins the exact compatible versions it installs and records them in the ledger; nothing here is a promise that today's latest stays compatible.

## 7. Decided architecture

### 7.1 Topology and naming

One Node process, `clio-coder web` at v0.5.0, `node --import tsx apps/clio-coder-web/server/main.ts` in the foundation. It binds `127.0.0.1` on an ephemeral or requested port, serves the built client from `dist/client/`, serves `/api/**`, hosts two domain worker threads (reads, ops), and supervises zero or more `clio-coder acp` children. It runs in the foreground and stops on Ctrl+C; `--idle-exit <ms>` (off by default) lets a desktop launcher run it without a terminal. Ordinary `clio-coder` invocations never start it.

Names: workspace package `@iowarp/clio-coder-web` in `apps/clio-coder-web/`; product name shown to people `Clio Coder`; command `clio-coder web`; app-owned state under `<clio state dir>/web/`; log prefix `[clio-coder:web]`. The product and package are not named workbench, GUI, or daemon; the words themselves are fine in prose. Naming is not a blocker; the ledger records any rename.

Directory shape (a proposal; none of these files exist at the reviewed SHA, and S1 creates them):

### 7.2 Process and thread ownership

- **HTTP process.** Hono app, event hub, operation registry, session supervisor, static files. Its `src/**` imports are an explicit allowlist, all asynchronous or trivial: `src/engine/acp/transport.ts`, `src/engine/acp/errors.ts`, `src/engine/acp/types.ts`, `src/core/xdg.ts`, `src/core/package-root.ts`, `src/core/process-identity.ts`, `src/domains/lifecycle/version.ts`. These live in `server/clio/http-shims.ts` so the allowlist is one file.
- **Domain workers** (`node:worker_threads`, restarted on crash). Two, so a long mutation never queues ahead of a read. The **reads worker** hosts every query adapter (trace, toolchain status, settings layers, session history, fleet, evidence, config graph, interop, doctor). The **ops worker** hosts mutating or long adapters (`installTool`, `removeTool`, anything that unpacks or writes). RPC is `{id, method, params, deadlineMs}` in, `{id, ok, result}` or `{id, ok: false, problem}` out, plus `{id, progress}` frames. Each worker has a bounded pending queue (64; a 65th request is refused with `unavailable` and `Retry-After`) and each call carries a deadline (reads 10 s by default, trace reads 15 s, ops per operation kind). A deadline that expires returns `unavailable` to the caller while the worker finishes its synchronous call and discards the result; synchronous work cannot be interrupted and the design does not pretend otherwise. Worker entry files are explicit modules (`server/worker/reads-main.ts`, `server/worker/ops-main.ts`) so packaging can emit them as their own entries.
- **ACP children.** One `clio-coder acp --cwd <root> --permission-timeout <ms>` per open session, spawned through `createStdioTransport`. Executable resolution in order: `CLIO_CODER_WEB_CLI` (absolute path to a CLI entry, for tests and fixtures), the checkout's `dist/cli/index.js` run with `process.execPath` when it exists, then `clio-coder` on PATH. The foundation prefers the checkout build so the app and the harness are the same commit. Children are terminated (SIGTERM, then SIGKILL after the transport's grace) on session close and on server shutdown.
- **CLI mutation children.** Fixed argv, bounded stdout and stderr, time-limited, JSON parsed once, run through the operation registry in the HTTP process because they are asynchronous spawns. Never receive a string the browser typed as argv; identifiers are validated against contract regexes and then passed positionally. These are cancellable (SIGTERM).

### 7.3 Contracts

`contracts/` is plain TypeBox on the root's `typebox` line, no framework types. Each area exports request, response, and event schemas plus the derived `Static` types. `contracts/common.ts` defines `Problem` (RFC 9457 shape with a closed `code` enum), `PageCursor`, `Meta`. `contracts/events.ts` defines the SSE envelope `{v: 1, seq, at, type, payload}` and the discriminated union of event payloads. The server validates every request body and query with `Value.Check` and returns `422` problems with the TypeBox error path; responses are validated in tests, not at runtime. `scripts/openapi.ts` walks the route table and writes `contracts/openapi.json`; a test fails when the file is stale.

### 7.4 Transport, events, reconnect

`EventSource` provides automatic reconnection and carries `Last-Event-ID`. Everything else below is the app's responsibility and is specified so it can be tested.

- **Commands and queries.** JSON over `/api/**`. Long work returns `202 {operationId}` or `202 {turnId}` immediately.
- **Envelope and scope.** Every event is `{v: 1, epoch, seq, at, type, payload}`. `epoch` is a random id minted at server start; `seq` is a process-monotonic counter starting at 1 within that epoch. The SSE `id:` field is `${epoch}:${seq}`. Sequence numbers are global to the server, not per resource, so one cursor covers every topic.
- **Ring buffer and eviction.** The hub retains at most 4,096 envelopes and at most 8 MiB of serialised envelope bytes, whichever bound is hit first. When a reconnect asks for `Last-Event-ID` or `?after=` whose epoch differs or whose `seq` is older than the oldest retained envelope, the server sends `resync {epoch, seq, reason: "epoch" | "evicted"}` as the first event and replays nothing. Otherwise it replays every retained envelope with `seq` greater than the cursor, in order, then continues live.
- **Two resource kinds.** *Projected* resources (sessions and their turns, operations, live install state) are owned by an in-memory projection in the HTTP process that increments its own `revision` every time it emits an event; the event payload carries `{resource, revision}`. *Fetched* resources (trace runs, evidence, fleet, settings, anything answered by a worker) have no server-side projection; their events are invalidation hints and the client refetches, so no delta is ever applied to them and there is no ordering problem.
- **Snapshot versus subscription for projected resources.** The client opens the global stream first and receives `hello {epoch, seq}`. While a snapshot request is pending, the client buffers every event for that resource. The snapshot response carries `X-Clio-Epoch` and `X-Clio-Revision`, where the revision is the projection's own revision read under the same synchronous step that assembled the snapshot, never the hub's `seq` at response time and never a value stamped onto an asynchronous worker result. The client installs the snapshot, then replays buffered events whose `revision` is greater than the snapshot's, in order, and drops the rest. An event from a different epoch triggers a refetch. Acceptance test: hold a snapshot response open in the server (test hook), deliver a turn delta while it is held, release the response, and assert the client state contains the delta exactly once.
- **Restart and epoch change.** A new server process is a new epoch. `resync` on reconnect makes the client `invalidateQueries()` for everything. Operations are in-memory and are gone; `GET /api/operations/:id` for an old id is `404` and the client renders "lost when the server restarted". On graceful shutdown the supervisor closes every ACP child (SIGTERM, then SIGKILL after the transport grace) before the process exits. Abrupt death is different and is not assumed away: `createStdioTransport` spawns children detached in their own process group on POSIX, so a killed server can leave a live `clio-coder acp` behind. The supervisor therefore records, in `<state>/web/children.json`, one row per child with the owning server's instance id, pid, and birth token, and the child's pid, birth token, session id, and workspace id, writing the row before `initialize` and removing it when it reaps. On start, a server reconciles that file and may terminate a recorded child only when the row's owning server is proven dead (its pid is not alive, or its birth token no longer matches, through `processAlive` and `processBirthToken` from `src/core/process-identity.ts`, added to the HTTP-side allowlist) and the child's pid still carries the recorded birth token (so a reused pid is never signalled). A live owner's children are never touched, so two web servers on one state directory cannot reap each other's sessions. Processes without a row are never candidates: the operator's CLI, TUI, and any other ACP host are invisible to this reconciliation by construction. Each recovered child is reported as `recovered orphan`. A session whose child is not owned by the current server is `state: unknown` until reconciled; the canonical session ledger under `<state>/sessions/` is never touched by the app, and reloading the session goes through ACP `session/load` exactly as after a Ctrl+C on the CLI. Acceptance tests (S3): kill-parent (server killed, child survives, next server reaps it); two live servers on one state directory (neither reaps the other's child); pid reuse (a row whose child pid now belongs to a different process with a different birth token is dropped without a signal).
- **Terminal states.** `operation.finished` and `turn.finished` events carry the terminal record in the payload, and the same record is fetchable by id for the retained window (256 finished operations; turns until the session closes). A client that reconnects after the terminal event was evicted from the ring learns the outcome from the snapshot, never from an inferred absence.
- **Byte bounds.** Per-operation progress is capped at 256 entries and 64 KiB (oldest entries collapse into one "n earlier lines omitted" marker); a session's turn projection caps cumulative streamed text at 1 MiB per turn and marks truncation, the same bound the workbench used; each worker admits at most 64 queued calls.
- **Heartbeat.** A comment frame every 15 s.
- **Resource streams.** `GET /api/traces/runs/:runId/live?after=<rowid>` tails one run through the reads worker's 500 ms poll (the loop `trace tail --follow` uses) and closes two idle polls after the run reaches a terminal status. Its cursor is the SQLite rowid, not the hub sequence, because the trace store owns that cursor. Session turn deltas ride the global stream because the client needs them on every page.
- **Snapshots are the source of truth.** The server keeps a per-session turn projection (timeline, active turn, pending permission) so `GET /api/sessions/:id` is always complete; events are deltas over it. Turn text chunks are in the ring buffer; E2 measures whether that is worth it or whether chunks should be replay-exempt with the projection covering reconnects.
- **Connection budget.** One global stream plus at most one resource stream per page, inside the six-per-origin HTTP/1.1 limit.

### 7.5 Trace access and pagination

Runs list: `GET /api/traces/runs?limit<=200&cursor=<opaque>&source=&status=&q=`. Keyset over `(started_at DESC, run_id DESC)`; the cursor is base64url JSON of the last row's pair. Implemented as app-owned parameterised SQL prepared on `TraceReader.db` inside the worker, after `TraceReader`'s own open, schema, and WAL checks have passed. This is private coupling to schema v1, which `docs/architecture/trace-store.md` publishes as a contract, and it is the same coupling `apps/trace-viewer/server.mjs` carries today. Proposed root seam for R2: `TraceReader.runsPage({before, limit, filter})`, at which point the app SQL is deleted. Events use the existing rowid cursor. Receipts and the evidence index come from `<stateDir>/receipts/<runId>.json` and `readEvidenceIndex(stateDir)`, with the five large receipt fields omitted from the run page and served by `GET /api/traces/runs/:runId/receipt?include=full` on demand.

### 7.6 Operation lifecycle

`OperationRegistry` in the HTTP process: `{id, kind, status: queued|running|succeeded|failed|cancelled, cancellable: boolean, startedAt, finishedAt, progress: [{at, message}], result?, problem?}`. Retention keeps every `queued` or `running` operation regardless of count and at most 256 finished records for the current epoch; eviction never touches a live operation. Clients send `Idempotency-Key` on every mutating POST. Keys are scoped to `(kind, workspace or installation scope)` and stored with a fingerprint (SHA-256 of the canonical JSON of path, params, and body); a repeated key with the same fingerprint returns the existing operation, and a repeated key with a different fingerprint is `409 conflict`. This is at-most-once within the current server epoch and nothing more; it is not durable exactly-once, and a client that retries across a restart may re-run an operation that already completed. Events `operation.progress` and `operation.finished`. `cancellable` is decided per kind at creation and is truthful: a CLI child operation is cancellable (SIGTERM through the runner); a toolchain install is **not**, because `installTool` accepts no `AbortSignal` and its unpack is synchronous, so the client shows no cancel control for it and `POST /api/operations/:id/cancel` answers `409 unsupported`. Reads are never operations; a read that outlives its deadline fails with `unavailable` and is retried by the client, and the worker discards the late result.

### 7.7 Error model

`application/problem+json` everywhere: `{type, title, status, detail, code, instance?}`. `code` is a closed enum in `contracts/common.ts`: `validation`, `unauthorized`, `not_found`, `conflict`, `unsupported`, `unavailable`, `upstream_acp`, `operation_failed`, `internal`. ACP `_meta` error codes map to `upstream_acp` with the remote code in `detail`. Stack traces and child stderr never reach the client; they go to the server log with the problem `instance` id for correlation.

### 7.8 Resource scope and authorisation

- Scope: the Clio installation this process runs as (config, data, state, cache from `src/core/xdg.ts`), the checkout or package root for docs, and the workspace roots the operator opens. A workspace root is an absolute path the operator supplies, validated as an existing directory and canonicalised with `realpath`. No other filesystem path is accepted from the client.
- Authorisation: bind `127.0.0.1` only; a 256-bit per-launch token printed in the launch URL fragment, held by the client in `sessionStorage`, sent as `Authorization: Bearer` on fetch and as `?token=` on `EventSource`; `Host` must be loopback and `Origin`, when present, must equal the server origin; no CORS. Static assets are served without the token; every `/api/**` route requires it. `--token <value>` exists for scripts and the REST milestone.
- Deep links: identifiers are validated by shape (`^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`) and then looked up; a miss is `404`. The workbench's snapshot-window allowlist is retired (section 10).

### 7.9 Source, build, install boundaries

Foundation (checkout only): server and workers run from TypeScript source through `tsx` (`node --import tsx server/main.ts`; worker threads inherit `execArgv`, which E1 verifies in S1); client is built by Vite into `apps/clio-coder-web/dist/client/`; tests run with `node --import tsx --test`. The app's `package.json` declares its own dependencies; `pnpm install` from the root updates `pnpm-lock.yaml` (the one unavoidable root file). Root imports are written against real module targets under `<repo>/src/` (for example `<repo>/src/domains/observability/trace-store.ts`); the relative depth from `apps/clio-coder-web/server/clio/` is `../../../../src/`, and S1 proves resolution with a test rather than this document asserting it.

v0.5.0 (root integration, enumerated in section 8 and `SPRINT.md` slices R1 to R4): root tsup gains three entries, `web/server → apps/clio-coder-web/server/main.ts`, `web/reads-worker → apps/clio-coder-web/server/worker/reads-main.ts`, `web/ops-worker → apps/clio-coder-web/server/worker/ops-main.ts`, because `new Worker(new URL(...))` cannot resolve a worker module that bundling did not emit; the server locates its workers beside itself by URL. `hono` and `@hono/node-server` join root `devDependencies` and `noExternal` (or `dependencies`, if bundling them proves worse; decided in R1 by measurement). The root build copies the Vite output to `dist/web/client/`. `files` and `scripts/release-manifest.json` gain `dist/web/**`. `src/cli/web.ts` registers `web` in `COMMAND_HANDLERS` and imports `dist/web/server.js` by URL beside itself. `tests/smoke/installed-package.test.ts` gains a case that installs the packed tarball into a scratch prefix with no `tsx` and no checkout on the path, starts `clio-coder web`, reads `/api/meta`, exercises one reads-worker call and one ops-worker call, and checks that `resolvePackageRoot()` inside the server and inside each worker returns the installed package root. Version matching is structural (one package, one commit) and checked anyway: `GET /api/meta` returns `{clio, app, apiVersion}` and the client refuses an `apiVersion` it was not built for.

### 7.10 Process and network policy (what replaces the Deno grants)

The workbench ran under `--allow-net=127.0.0.1` and `--allow-run=clio-coder,kill,xdg-open`. Those were real, runtime-enforced egress and spawn allowlists, and Node has no equivalent switch for network egress. The replacement is explicit policy in code with tests that fail when it is violated:

- **One spawn chokepoint for application-owned process creation.** `server/process-policy.ts` is the only app production module that imports `node:child_process` or constructs a `Worker`; a boundary test checks the app's production modules. It exposes fixed-shape functions for starting the two domain workers, `spawnClioAcp(root, permissionTimeoutMs)`, `runClioCommand(argv)` (fixed argv from a closed table, identifiers validated by regex), and `openBrowser(url)` (`xdg-open`, `open`, or `cmd /c start`, only when `--open` was given). Existing root seams still spawn internally, including ACP transport and version probes; the source import allowlist accounts for those paths. This is an app boundary, not a claim that imported root code never spawns.
- **Bind policy.** The listener binds `127.0.0.1` only; `--host` does not exist. A test asserts the bound address and that a request with a non-loopback `Host` is refused with `421`.
- **Egress policy.** The server process performs no outbound network requests except `installTool`'s downloads. `server/clio/adapters/toolchain.ts` passes an explicit `fetch` whose allowlist is derived from `PINNED_TOOLS` download and document URLs; a test injects a URL outside the pin and asserts refusal before any socket opens. The test suite runs with `globalThis.fetch` replaced by a function that throws, so any other egress fails the suite.
- **Filesystem policy.** Reads and writes are limited to the Clio roots from `src/core/xdg.ts`, the package or checkout root for docs and assets, and canonicalised workspace roots the operator opened. Path parameters never reach `fs` without `realpath` containment (`isWithin`, the same shape `src/cli/docs.ts` uses).
- **Bounded experiment E8.** Run the server under Node's permission model (`node --permission --allow-child-process --allow-worker --allow-fs-read=<roots> --allow-fs-write=<roots>`), starting with `--permission-audit` to learn the real access set. Decision rule: adopt as the desktop launcher's default if `tsx` loading in the foundation and the bundled entries at v0.5.0 both run cleanly under it; otherwise document that runtime enforcement is code-level only.

## 9. Desktop intent, stated honestly

What exists: a Linux-only `deno compile` binary (~105 MB) plus a freedesktop entry; native Windows launch refused in `main.ts`; the `deno desktop` webview task unverified; nothing for macOS. Those are the only desktop facts that have been measured. Everything below is a verification target for the new app, not a claim.

- **Foundation: browser launcher.** `clio-coder web --open` (foundation: `node --import tsx server/main.ts --open`) prints the loopback URL carrying the token and opens the default browser through the same `xdg-open`, `open`, `cmd /c start` shape `src/cli/docs.ts` uses. Verification target: Linux and WSL2 (this machine) in S9. macOS and Windows use the same code path and stay marked unverified until a session on that platform runs it.
- **v0.5.0 desktop visibility after a normal install: the launcher.** `clio-coder web launcher install | status | uninstall` writes, checks, and removes a platform launcher that runs `clio-coder web --open --idle-exit 60000`. Linux: a freedesktop `.desktop` entry under `$XDG_DATA_HOME/applications` with `Terminal=false`; verification target in S9. macOS and Windows: the subcommand refuses with a message naming `clio-coder web --open` as the supported path until a session on that platform verifies a `.app` wrapper or a Start Menu shortcut and removes the refusal. `--idle-exit` stops the server when no client has been connected for the given time and no operation or live turn is running; a live turn holds the process. `src/cli/uninstall.ts` learning about the launcher file is a class C change in R4.
- **PWA: deferred.** An installed web app remembers an origin. This design uses an ephemeral port by default, a per-launch token held in `sessionStorage`, and a foreground server that exits, so a PWA icon can neither start Node nor discover the next origin and token. No installable window is promised. S9 may run one bounded experiment (E5): a launcher mode with a fixed port and a token the launcher rewrites into the served page, then the lifecycle close server → click icon → live authenticated app. Only if that passes end to end does a PWA manifest ship; otherwise the desktop entry is the whole desktop story.
- **No daemon.** Ordinary CLI, TUI, and ACP startup does not start the server. Explicit web launch actions, including the docs navigation command after R3, may start it. `clio-coder web` is foreground and stops on Ctrl+C. There is no socket activation, no background service, no auto-start on login.
- **Native shell.** Electron, Tauri, and `deno desktop` are out of scope through v0.5.0.

## 11. Bounded experiments and decision rules

| Id | Question | Method | Decision rule |
| --- | --- | --- | --- |
| E1 | Do `worker_threads` inherit `--import tsx` reliably for the source-run foundation? | S1 starts both workers under tsx and runs one call each | Pass: keep threads. Fail: switch the worker host to `child_process.fork` with the same RPC; no other design change |
| E2 | Is replaying turn text chunks from the ring worth it? | S4 measures ring occupancy against the perf workload's ~1,400 chunks per turn and a forced reconnect mid-turn | If a mid-turn reconnect resumes cleanly from the projection alone, mark `turn.text` replay-exempt and shrink the ring |
| E3 | What does one ACP child cost per open session? | S3 records RSS and boot time of `clio-coder acp` on this machine, three children open | Set the default concurrent-session cap from the measurement; if it is prohibitive for a desktop launcher, prototype the single-workspace in-process mode through `BootOptions.acp.transport` as a later slice, never as the default |
| E4 | Does the Hono plus route-table design deliver what section 6.3 estimates? | S1 measures the real glue line count, verifies query and path parameter parsing against the table, verifies typed handler inputs and outputs, and validates the emitted `openapi.json` with an OpenAPI 3.1 validator (parameter and path assembly and the JSON Schema dialect are the risky parts); S4 runs the streamed-turn workload through the global SSE stream | Any correctness or backpressure defect Hono cannot express, or glue that lands far above the estimate, moves `server/http/**` to Fastify; the table, projections, and services stay |
| E5 | Can an installed PWA icon relaunch into a live, authenticated app? | S9, after the launcher works: fixed launcher port, token delivered by the launcher-served page, then close the server, click the icon, expect a live authenticated app | Ship a manifest only if that lifecycle passes end to end; otherwise the desktop entry is the desktop story and PWA stays deferred |
| E6 | Poll or watch for live trace events? | S2 ships the 500 ms worker poll; a later session may try `fs.watch` on the WAL file | Adopt watch only if it reduces latency without missing events in the tail test |
| E7 | Does the route-table typed client stay ergonomic at forty routes? | S1 and S2 write against it | If inference becomes slow or unreadable, split the table per area; codegen remains out |
| E8 | Can the server run under Node `--permission`? | S9, starting with `--permission-audit` | Adopt for the launcher if source-run and bundled modes both pass; otherwise document code-level enforcement only |

## 12. Deliberately not done

No distributed infrastructure, no queue, no database beyond Clio's own files, no migrations, no compatibility readers for workbench or trace-viewer state, no state importer, no parallel implementation kept alive for the old apps, no compatibility aliases (R2 removes `trace ui`; the `clio-coder docs` command that R3 keeps is a canonical navigation command into the app, not legacy support), no new source of truth for Clio state (app state is a recent-workspaces list and nothing that Clio owns), no auto-started daemon, no native shell, no multi-workspace orchestrator host, no copying of admission logic out of CLI commands, no export additions under `src/` during apps-only slices.

## 13. Open decisions and disagreements for Astra

1. **Hono over Fastify** (section 6.3). The disagreement is real and bounded; E4 is the exit.
2. **Two domain workers rather than one** (section 7.2). Costs one more module graph in memory; buys reads that never wait behind an install.
3. **Retiring the host-only payload policy** (section 10). This is a threat-model change: the browser on loopback holding the launch token is the operator. If Astra or the operator wants event payloads or receipt fields withheld from the browser regardless, that is a one-line filter in the trace adapter and the trace explorer becomes correspondingly less useful; say so explicitly rather than inheriting the old rule by default.
4. **Settings mutation in the foundation** is limited to the four safe keys through a live session's ACP `settings/patch_safe`. Target use and remove, evidence build, and later library install and remove go through fixed-argv CLI children in S7b, S8b, and S8d; their success is modelled by exit code plus a typed follow-up read, never by parsing their terminal prose. Whether v0.5.0 should add root seams for these instead is an R-slice decision.
5. **`docs/html` at v0.5.0.** The blueprints are 2.2 MB and excluded from npm today. Recommendation: keep them checkout-only and make the shipped Markdown tree the canonical docs surface; revisit only if the tarball budget and the value both justify shipping them.
6. **Naming.** `clio-coder web`, `@iowarp/clio-coder-web`, `<state>/web/`. Not a blocker.
