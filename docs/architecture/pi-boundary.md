# Pi SDK Boundary

Clio Coder pins Pi 1.0.0 as its provider, agent-loop, and terminal SDK. This
page describes SDK primitives and Clio-owned behavior. Review these boundaries
when upgrading Pi.

## Pins, patch, and API snapshot

- **Pins.** `package.json` lists `@earendil-works/pi-agent-core`, `@earendil-works/pi-ai`, and `@earendil-works/pi-tui` under `dependencies`, each at the exact version `1.0.0` with no range. Neither pi-coding-agent nor pi-durable is a dependency.
- **One patch.** `pnpm-workspace.yaml` carries a single `patchedDependencies` entry, `'@earendil-works/pi-tui@1.0.0': patches/@earendil-works__pi-tui@1.0.0.patch`. pi-agent-core and pi-ai run unpatched. The patch has 15 hunks in 10 `dist/` files: semantic `applyEdit` operations on `Editor`, `Input`, and the search overlay, public search and prompt-navigation methods on `TuiAltScreen`, a wrapping fix in `wrapTextWithAnsi`, and the `TuiMainScreen` render reset memo with its Kitty image-row scans (5 hunks in `tui-main-screen.js`). The memo and image-row hunks stay in the patch. Without them a 22.9k-row regular-screen transcript costs 5.90 ms per keystroke frame instead of 0.62 ms. The build bundles the patched pi-tui (`noExternal` in `tsup.config.ts`), so an npm consumer needs no pnpm and no patch step. The [patch notes](../../patches/README.md) list every hunk and its alternatives.
- **Consumed API snapshot.** [pi-surface.json](../pi-surface.json) records signature hashes for every export of each Pi entry point Clio imports, with `schemaVersion: 1` and all three packages at `1.0.0`: pi-agent-core has 1 entry point and 42 exports, pi-ai has 26 entry points (the root and 25 deep ones) and 334 exports, and pi-tui has 3 entry points (the root, `dist/keys.js`, `dist/utils.js`) and 205 exports. The scan reads static imports, so the dynamic `pi-ai/compat` import is not in it. `pnpm pi:surface-diff` compares the snapshot with the installed packages, `pnpm pi:surface-snapshot` rewrites it deliberately, and `pnpm lint` runs the comparison even when the version is unchanged.

## Transcript ownership

`Agent.state.systemPrompt` is a
read-only projection of system messages. Pi's `normalizeContext` folds legacy
`systemPrompt` and `tools` into a leading system message; it **does not deduplicate**
a transcript that already contains that baseline. Clio therefore sends native
transcripts with `messages` only and builds legacy prompt/tool snapshots only
where a Clio-owned consumer needs them.

| Pi surface | Clio adaptation and reason |
| --- | --- |
| `normalizeContext`, `getCurrentSystemPrompt`, `getCurrentTools` | [context.ts](../../src/engine/context.ts) delegates section patches, prompt concatenation, and tool additions/removals to Pi. Native API dispatch and OpenAI completions preserve the transcript; Ollama's custom wire and worker request projection consume the resolved snapshot. Clio does not implement its own transcript reducer. |
| `createInitialSystemMessage`, `toToolDeclaration` | Session replay and prompt recompilation replace Clio's complete baseline through `replaceEngineMessages` / `setEngineSystemPrompt`. Clio persists her compiled prompt and conversation separately, so rehydration produces one baseline, not a second prompt appended to the old one. Executable tools remain in `state.tools`; only portable declarations enter messages. |
| Parent-to-worker context and tool-free side rounds | Fork/splice capture excludes parent system/tool declarations before validating complete conversation batches. The child retains its own compiled prompt and executable loadout. Side-question and handoff rounds similarly drop session system entries before installing their own tool-free prompt. First-turn middleware counts conversation only. |
| `AgentLoopTurnUpdate.context` | Post-tool compaction returns the complete rebuilt transcript and executable tools. The active loop receives the new prompt and retained conversation before its continuation. No top-level `systemPrompt` is carried on that context. |
| System messages in `Agent.state.messages` | Conversation accounting, measured-anchor indexes, snapshots and replay comparisons exclude system entries because system text and schemas already have their own budget categories. Worker result offsets are measured after Agent construction, excluding the injected baseline and every inherited message. |
| `getToolStateChanges`, public context transforms, `convertToLlm` | Warming copies the transcript, declares changed executable tools using Pi's diff, then applies the same transforms and conversion as a real turn. Transformed system messages and tools reach the provider intact. Warming never executes tools or appends its response to the session. Local residency, foreground ownership, input limits and billing admission remain Clio policy. |
| `resolveTranscript` and provider compatibility flags | Pi decides whether a model receives mid-conversation system messages/tool additions or a collapsed request. The completions wrapper transforms assistant reasoning without flattening system history. Legacy custom stream delegates still receive a resolved request snapshot for compatibility. |
| Retry and overflow behavior | Clio inherits Pi's Cloudflare 520/Azure transient-error classification and z.ai overflow detection. Capped exponential delay uses Pi's public `retryDelayMs` for turn retries and worker-run retries, and stream overflow is classified from the full error message with Pi's `isContextOverflow`. Model-loading floors, cancellable UI countdowns, stream-stall limits and `Agent.continue()` recovery remain Clio-owned. |
| Cache retention and provider request assembly | Pi owns native cache-control fields and provider-specific retention behavior. Clio supplies target policy, session identity, local-runtime fields and measured cache telemetry. Upstream coding-agent prompt warming is not a public pi-agent-core/pi-ai warm API and does not replace Clio's local-only admission and lifetime rules. |
| Meta provider and Muse OAuth | Environment-key parity includes `META_API_KEY`. Clio's explicitly selected provider catalogs and OAuth flows stay tied to supported runtime descriptors; out-of-tree runtime plugins can use the public Pi provider factory. |

## Architecture boundary enforcement and tests

The rule keys on the `@earendil-works/pi-` prefix, and it is a single rule with
no exceptions: only files under `src/engine/**` may import a `@earendil-works/pi-*`
package, type-only imports included. The allowlist of type-only exceptions
(`allowedPiTypeImportSpecifiersOutsideEngine`) is deliberately empty. Everything
else, `src/interactive/**` included, reaches Pi through engine re-exports such as
[tui-primitives.ts](../../src/engine/tui-primitives.ts), and domains take erased engine shapes
(`EngineModel`, `Api`, `Model`) from [types.ts](../../src/engine/types.ts) and [ai.ts](../../src/engine/ai.ts).

[check-boundaries.ts](../../tests/boundaries/check-boundaries.ts) enforces this statically over the import
graph as rule 1 of seven. The other six cover the worker's domain imports, domain
extension access, tools staying independent of `src/interactive/**`, the chat loop
never importing `src/entry/**`, turn-control purity, and the Stage 0 closure
(rule 6). [engine-lifecycle.test.ts](../../tests/contracts/engine-lifecycle.test.ts)
covers agent-loop ordering, reset, tool-argument normalization, the keybinding
table and alt-screen render seams; [tool-boundaries.test.ts](../../tests/contracts/tool-boundaries.test.ts)
covers tool schema admission and execution isolation across runtimes.

### Stage 0 seams and the chunk budget

The instant shell's Stage 0 closure is the static import closure of the chunk
that holds `src/interactive/terminal-lease.ts` (`STAGE_0_OWNER`), which is what a cold
`clio-coder` start pays before it can draw anything.
[instant-shell-import-graph.test.ts](../../tests/contracts/instant-shell-import-graph.test.ts)
walks the built chunks and holds that closure to 32 chunks, 1,400,000 total bytes,
and 350,000 Clio source bytes. It fails only after a full build, so rule 6 guards
the cause statically: a second, disjoint reacher of a module inside the closure
makes esbuild split the chunk the closure sits on. Any value importer outside the
closure and the protected `src/interactive/**` and `src/engine/**` trees reaches
those trees only through a module declared in `STAGE0_SEAMS`, each with its
architectural reason, and a seam may not lead back into Stage 0 unless a
composition-root overlap is declared explicitly. Engine modules that the CLI,
domains, or tools value-import, such as `tui-primitives.ts`, `oauth.ts`,
`env-api-keys.ts`, `ai.ts`, `api-registry.ts`, `prompt-templates.ts`, `truncate.ts`,
and `types.ts`, are declared seams. A new engine module that code outside
`src/engine/**` needs must be declared with its reason and must keep its value
closure off the render graph. `text-wrap.ts` is a leaf for the same reason: the
shutdown notice sits inside the Stage 0 closure and may not drag the pi-tui root in.

### Dynamic compat bridge

`pi-ai` registers API providers in a process-global registry that an out-of-tree
runtime plugin may rely on. [api-registry.ts](../../src/engine/api-registry.ts)
dispatches through its own api-keyed registry over Pi's lazy API factories, and
`activateExternalPluginApiBridge` is the only place it imports `@earendil-works/pi-ai/compat`,
dynamically. The loader calls it before importing an out-of-tree runtime: each
package listed in `integrations.runtimePlugins` and each `.js` file under
`<config dir>/runtimes/`. With neither present the bridge never loads and costs
nothing. When it loads, Clio mirrors her non-built-in registrations into Pi's
registry before plugin evaluation and routes later dispatch through it, so a
plugin's registrations keep their last-writer-wins order. Removing the bridge
would break `integrations.runtimePlugins`, so it stays.

### Claude Agent SDK external

`@anthropic-ai/claude-agent-sdk` is an `optionalDependencies` entry, not a Pi
package, and `tsup.config.ts` lists it in `external` (with `node:sqlite`).
`tsup` externalizes `dependencies` by default but not optional ones, so without the
entry esbuild would bundle the 224 MB package into `dist/` and make it a hard
requirement. Staying external keeps the lazy `await import()` in
[sdk-module.ts](../../src/engine/claude/sdk-module.ts) a real runtime import; the
install and first-use behavior are in
[the interoperability guide](../guide/interop.md#claude-agent-sdk-runtime).

## SDK upgrade checks
