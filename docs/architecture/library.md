# Library architecture

The [library guide](../guide/resource-library.md) explains package installation and operator controls. [authoring-plugins.md](../guide/authoring-plugins.md) owns the manifest fields.

Clio Coder uses **library** for the collection and **package** for a distributable item. This name covers both local authoring and indexed distribution without suggesting a remote store or a purchase. CLI `library`, slash `/library`, the Library overlay and the bundled `library/registry.yaml` describe the same collection.

## Invariants

1. **One identity.** A content package has a portable root `plugin.json`, one lowercase portable name and one explicit bounded Semantic Version. Its kind is the `kind` of the Clio namespace, `extensions["ai.iowarp.clio"]`, defaulting to `plugin`. Content kinds are `plugin`, `skill`, `agent`, `prompt`, and `playbook`. The sixth kind, `extension`, has a `clio-coder-extension.yaml` manifest and its own state (invariant 12). One name owns one installation directory per scope; changing kind requires removal.
2. **One envelope.** Plugins may carry many public components. Single-component kinds declare exactly one public component of their kind, expose exactly that file in their resource root, and can carry private supporting files (see [package kinds](../guide/authoring-plugins.md#package-kinds)). Authoring templates live in `library/_authoring/templates/` outside the kind roots so they never enter the distribution catalog.
3. **One integrity rule.** The package digest is a SHA-256 over every file, directory and link in sorted relative-path order, framed by entry kind, path and byte length, so it covers manifests, scripts, references, names and empty directories. Symlinks must resolve inside the package and their target text is part of the digest; hard links, special files and a symlinked package root are refused. The same digest function frames extensions, so a digest computed by one engine is comparable to the other. Staging and publication recheck the digest. Neither force nor pin silently approves a changed indexed source. Installed drift revokes resource admission. Validation is strictly read-only: it checks manifest schemas, payload contracts (strict v1 agent schemas with custom audience, playbook DAGs, prompt loadability), acyclic package references (`${component:...}`, `${pluginRoot}`), and environmental prerequisites without modifying source bytes or state.
4. **One durable state.** The plugin engine owns complete packages at user scope (`<configDir>/plugins/<name>/`) and project scope (`<cwd>/.clio-coder/plugins/<name>/`). Each scope's `plugins/state.json` records kind, source, structured origin, trust, install time, the verified digest, and the disabled list. Atomic staging, a per-scope mutation lock, preimage checks and recovery copies apply to every kind. There is no library-specific installer or per-kind pin store. Extensions keep the same guarantees in `extensions/state.json` beside their installed packages.
5. **One workspace picture.** Library discovery combines the bundled, user, project and explicitly selected indexes with installed state. The list and overlay show disabled, damaged and shadowed copies. Effective loading uses one precedence rule: valid, compatible copies compete and the project copy wins, so a disabled project copy still suppresses the user copy. An invalid project copy does not hide a valid user copy, and neither does a project copy blocked by workspace trust (invariant 11). Explicit scope always selects exactly one copy.
6. **One dependency rule.** Manifest and index package requirements agree, are typed, and form a finite acyclic graph. Only enabled, verified packages satisfy dependencies. Install can plan missing dependencies with explicit inclusion; existing inactive dependencies require repair. Disable and remove refuse when an enabled dependent would lose a satisfied requirement. Atomicity is per package, not a transaction across a dependency graph.
7. **Trust follows origin.** Each install record carries a structured origin and a trust of `trusted` or `foreign`. Origins `local`, `catalog` and `github` install as trusted. Origins `interop` (`{host, source: absoluteOriginalPath}`, from `interop adopt`) and `import` (`{transport, format, source}`, from `library import`) always install as `foreign`. `installLibraryPackage({kind, sourcePath, scope, origin, trust, ...})` is exported from [index.ts](../../src/domains/plugins/index.ts). Skill and prompt loaders admit a foreign package only while `integrations.projectResources.trustProjectImports` is true, at either scope, and that setting never activates loose compatibility roots. Generic updates and forced replacement of foreign content refuse until explicit removal and reviewed re-adoption. Package trust records the origin of a copy and is independent of the operator's consent to a project's install state, which is workspace trust (invariant 11).
8. **Operator authority remains separate from autonomy.** Active resource trees (`.clio-coder/{skills,plugins,extensions}/` and the same names under `<configDir>`) are operator-owned: model writes, edits and deletes there are refused for the main agent and for workers at autonomy `default`, and reads stay allowed. At `yolo` only the yolo floor holds, which still refuses them under Clio's own config directory (`clio-owned-state`) but not in the project's `.clio-coder/` trees. A model shell call is inspected for the operator CLI. The mutation verbs of `clio-coder extensions` (`install`, `update`, `remove`, `enable`, `disable`, `pin`) and `interop adopt --yes` are blocked at `default` and admitted at `yolo`. `clio-coder share import` (without `--dry-run`), `clio-coder extensions test` and `clio-coder extensions validate` ask for one-shot operator confirmation in `default`, because an import installs packages from an archive the model may have written and the other two run a package's own code. Recognized `clio-coder library` mutations (`install`, `import`, `update`, `remove`, `enable`, `disable`, `pin`, `register`, `sync`, `push`, `remote`) ask for one-shot operator confirmation in `default`, which the safety judge never answers, and are admitted in `yolo`, and a headless run denies the ask. Read-only inspection and a `--dry-run` of `install`, `import`, `update`, `enable`, `disable` or `remove` stay available and never ask, because a dry run writes nothing. `clio-coder config trust` is blocked at every autonomy level as part of the yolo floor (`trust-authority`), so the model can never grant workspace trust. This is command inspection, not confinement of arbitrary scripts. Runtime offers and overlays commit only through their bound approval paths; the attended install rule is in [skills-marketplace.md](../guide/skills-marketplace.md#attended-install-rule). Source: [protected-artifacts.ts](../../src/domains/safety/protected-artifacts.ts), [skill-authority.ts](../../src/domains/safety/skill-authority.ts), and the `library-confirm` rule in [policy-engine.ts](../../src/domains/safety/policy-engine.ts).
9. **One inventory, two projections.** [library-inventory.ts](../../src/domains/resources/library-inventory.ts) produces the bounded, body-free record of packages, scoped copies and actual components. The CLI reads it for `library components` and the model reads it through `gateway(op="call", capability="clio_library", args={})`; they agree about ownership, runtime name, scope, origin, availability and invocation because they are the same records. The model projection is narrower, not different: it is the model audience, so internal and shadow agents, untrusted, invalid, shadowed and manual-only resources are absent, and it drops absolute component paths. A catalog `provides` hint is projected as its own tagged row that names its installable owner and that member's availability, and it never carries an invocation. Neither projection activates, installs, registers or pins anything, and neither fetches a remote source. A native worker registry has no admitted library projection and receives a clear unavailable read rather than the global library.
10. **One lifecycle plan.** Install, update, enable, disable and remove each build one reviewed plan with [library-actions.ts](../../src/domains/resources/library-actions.ts), which stages sources and writes nothing. Applying a plan rechecks every reviewed fact inside each scope's lock and refuses a changed fact as `stale_plan`, a held lock as `locked`, and a broken dependent as `dependents` (the apply outcome reports it as `refused`). A later step failing never undoes an earlier committed step. The result reports disk verification, component admission and host refresh as separate facts, and a failed refresh never undoes a committed write. The CLI and the TUI consume the same plan. For an extension step the plan carries the capability envelope read from the staged manifest (invariant 12).
11. **Project copies need workspace consent.** Project package digest checks prove integrity; workspace trust supplies consent. The `plugins` surface in [workspace-trust.ts](../../src/core/workspace-trust.ts) approves identities from `.clio-coder/plugins/state.json` for one canonical workspace. An identity includes the package id, content digest, envelope digest, source, origin, trust flag and plugin kind. It excludes install time and the disabled list. Reinstalling identical content, disabling or removing a package preserves consent; enabling an unapproved identity or changing an identity requires approval. Legacy records without a content digest still require approval of exact state-file bytes. An unapproved surface contributes no project resources, satisfies no dependency and never suppresses a user copy. An operator project install through the CLI, Library overlay or GUI can approve only the records it wrote when the prior state was absent or trusted; imports, interop adoption and skill install offers do not grant approval. A Clio-created task worktree can inherit its origin's approval when its enabled identities are covered, or its state is byte-identical to the approved origin. Extensions use the same contract for `extensions/state.json`. [resource-library.md](../guide/resource-library.md#workspace-trust-for-project-packages) describes review and reload commands.

12. **Plugins and extensions are separate packages.** A plugin is content and never runs code inside Clio Coder. An extension is Clio code in its own process, with its own manifest, digest, state file and consent. The operator reviews an extension's capability envelope, including the state it keeps and the prompts it takes over, before install and update. The install records the envelope digest, and it must match again when the install is applied and when the extension loads. An extension may name the one plugin it serves with `plugin: <name>`. That link alone makes `replaces: prompt` legal, and the takeover applies only while the plugin is installed and enabled. An extension root never holds `plugin.json`, and installing either package never installs the other. The plugin's prompts keep a working fallback for when its extension is absent. The envelope, the sandbox and the runtime are in [extensions](../guide/harness-extensions.md); [library-pairing.ts](../../src/domains/resources/library-pairing.ts) answers which partner a package has, so the browser, the plan and the CLI agree.
13. **Lifecycles leave bounded receipts.** Every committed install, update, enable, disable, remove, register, import and share import records a receipt with the operation, the package kind and id, the version, the content digest, the envelope digest for an extension, the scope, the source and the actor (`operator`, `model-confirmed` or `upgrade`). Only the most recent 512 receipts are kept in one file under the state directory, and the operation is also journaled as a `library.*` record in the process journal ([library-receipts.ts](../../src/core/library-receipts.ts)). A damaged receipt store never blocks browsing or admission, and a failed receipt write never undoes a committed change. The Library detail pane and `/extensions` show a package's last lifecycle.

## Identity at runtime

Package identity, component identity and invocation identity are distinct. The package reference is `kind:name`. A component reference such as `${component:agent:researcher}` is local to one package and resolves a contained file. It does not rename the agent. Prompt invocation names derive from paths beneath the prompt root with directory separators written as colons, agent IDs derive from agent filenames, and playbooks use their authored names. Authors must choose unique runtime names, normally with their package prefix. Installation does not add an automatic colon namespace to agents or playbooks.

For example, Materio uses `materio-*` agents and playbooks and `/materio:*` prompts; the WTF-P bridge uses `/wtfp:new-paper`, `/wtfp:map-project`, and `/wtfp:create-outline`. Runtime collisions use each resource loader's documented precedence and diagnostics; the skill and prompt rules are in [extensions-and-sharing.md](../guide/extensions-and-sharing.md#resource-roots-and-precedence).

## Owners and boundaries

`src/domains/plugins` remains the internal engine name because it implements the portable manifest, filesystem integrity, installation state and enabled resource roots. [library.ts](../../src/domains/resources/library.ts) composes discovery, registration, requirements and install plans. [library-actions.ts](../../src/domains/resources/library-actions.ts) owns lifecycle plans, [library-validation.ts](../../src/domains/resources/library-validation.ts) owns package validation, and [import.ts](../../src/domains/interop/import.ts) owns `library import`. CLI and TUI consume those functions. The resources domain handles loader-specific schemas, trust and activation; it does not establish a second managed package lifecycle.

Unmanaged local resource files remain discoverable in established Clio Coder and foreign roots. The worker's bounded raw-skill preparation helper and authoring audits are not library installations. Their normalized skill-body hashes describe activation and provenance evidence, not installable package integrity. Maintainer `skills:check` validates authored skill metadata and audit records; the release's distribution integrity rule is `library:check` over full package trees.

Package scripts versus extensions: plugins may carry contained scripts for explicit evaluation or verification workflows without registering runtime tools, hooks or session UI. [Extensions](../guide/harness-extensions.md) remain a separate executable integration contract with their own envelope, sandbox and lifecycle. They cannot own domain resource roots.
