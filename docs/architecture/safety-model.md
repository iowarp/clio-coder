# Clio Coder Safety Model

`createSafetyPolicyEngine` in [policy-engine.ts](../../src/domains/safety/policy-engine.ts) decides what a tool call may do. One admission evaluator, `evaluateAdmission` in [admission.ts](../../src/domains/safety/admission.ts), applies that decision and then the autonomy mapping in [autonomy.ts](../../src/domains/safety/autonomy.ts). The native tool registry ([registry.ts](../../src/tools/registry.ts)), the Claude SDK bridge and the ACP delegation mediator all decide through it, each translating its transport into the same input. The [tool usage guide](../guide/tool-usage.md) shows the operator surface, and [Choosing an autonomy level](../guide/commands-and-modes.md#choosing-an-autonomy-level) is the operator's how-to.

The registry enforces safety rules before admitted tool calls execute. The session prompt describes those rules to the model. Safety decisions, safety judge verdicts, aborts and session park or resume events are accountability events in the session and run telemetry journals ([decision-events.ts](../../src/domains/safety/decision-events.ts)).

## Execution boundary

Clio Coder gates tool calls before they run and confines some of them while they run. At autonomy `default` the main session's `bash` and `run_script` commands run inside the [main-session sandbox](#the-main-session-sandbox) when the host has an OS sandbox backend. The commands of a dispatched native worker run under the [worker OS sandbox](#worker-os-sandbox), and the runtime child of an api 2 extension runs under the OS sandbox when one exists ([extensions and plugins](#extensions-and-plugins)). Everything else runs with the operator's operating-system permissions: the main session's commands at `yolo` or on a host without a backend, typed tools such as `write` and `edit`, hooks, and external agents. Environment filtering controls inherited variables. Stronger isolation needs an external sandbox such as a container.

## Autonomy

Autonomy is the operator's grant to the main agent. There are two levels.

- `default` follows one rule: containment first, judgment second, asking last. Workspace edits and contained shell work run. Destructive work that a workspace snapshot can undo runs after the snapshot is taken. A call that escapes containment, or that a deterministic rule would stop, is reviewed by the [safety judge](#the-safety-judge) against the operator's own messages. The operator is asked only when the judge gives no verdict, after the judge has blocked repeatedly, or for a decision only the operator may make. An approval card or question nobody answers resolves after the [unattended timeout](#unattended-resolution).
- `yolo` is the skip-permissions mode. Only the [yolo floor](#the-yolo-floor), operator rules in an approved `.clio-coder/safety.yaml` and the run's ceilings block. Nothing asks, `ask_user` answers itself, and commands run unsandboxed; only `safety.sandbox: required` keeps scripts in a sandbox. The operator accepts it once, and it is refused as root outside a container.

Dispatched workers inherit the main session's level through their permit and keep their own OS sandbox; see [Workers at each level](#workers-at-each-level). A headless `clio-coder run` takes `yolo` only from its own `--autonomy yolo`; see [Headless runs](#headless-runs).

Only the operator sets the level: the user `settings.yaml` (`safety.autonomy`, default `default`), `/settings`, `clio-coder configure`, `--autonomy` on `clio-coder` or `clio-coder run`, the leader-key toggle (`y`) in the TUI, or the session mode of an ACP client. No tool, skill, worker or model output can raise it, and `configure_clio` refuses `safety.autonomy`. A project settings layer can only tighten: a project `safety.autonomy` that would loosen the user level, or is not a valid level, is ignored and reported as a layer issue, so a repository can ask for `default` when the user runs `yolo` but never the reverse.

### Admission order

The operator's own main session at `default` settles one call in this order. Steps 1 to 3 are blocks; the first step that settles the call wins.

1. **The yolo floor.** A floor hit blocks with reason code `yolo-floor:<rule id>`. No judge and no approval clears it.
2. **Run ceilings.** Write roots, an approved `.clio-coder/safety.yaml` that no longer parses, a read-only run, the turn's tool scope and an armed skill's tool surface refuse the call.
3. **Hard rails.** Path policy (zero-access, read-only, no-write and no-delete entries) and operator authority (workspace trust, Clio's settings, installed skills, plugins and extensions) block. A bash `cwd` outside the workspace blocks unless the call is contained.
4. **Containment.** A [contained call](#when-a-call-is-contained) runs without the asks that exist only because Clio cannot see what a command does.
5. **Recoverability.** A lone worktree discard, or a lone delete inside the workspace or a scratch root, runs after a [workspace snapshot](#workspace-snapshots-and-rewind) under reason code `snapshot-recoverable`.
6. **Asks.** Every other call the [rules table](#what-runs-what-is-judged-what-blocks) marks as an ask parks: former damage-control blocks, authored confirmation rules, outward actions, uncontained commands outside the recognized set, typed writes outside the workspace and the scratch roots, typed writes to the repository's git control files, and operator-only decisions.
7. **The safety judge.** An ask that is not operator-only goes to the judge first. An allow runs the call, a block refuses it back to the model, and no verdict falls through to the next step.
8. **The operator.** What remains reaches the approval card in the TUI or the ACP client's permission request. A headless run denies it.
9. **Unattended timeout.** A TUI card nobody answers within `safety.unattendedAfterSeconds` is denied and the turn continues.

Before an admitted call's body runs, the registry takes the snapshot its trigger asks for; see [Workspace snapshots and /rewind](#workspace-snapshots-and-rewind).

At `yolo` the order stops after step 2, with operator-authored rules added to the blocks. Everything else runs. A call that passed a rail which would have asked or blocked is journaled in its `tool.decided` record as `yolo-admitted:<reason code>`.

Workers, a main-agent grant of a worker's ask, scheduled command jobs, the Claude SDK bridge and the ACP delegation mediator do not get the operator's scope. They meet [the safety net](#the-safety-net) as written: damage-control blocks stay blocks, there is no containment relaxation and no snapshot, and asks follow their own route. A scheduled `main` job and a `main_turn` delivery run as turns of the operator's own session, so they get its scope.

### What runs, what is judged, what blocks

In this table "judge" means the safety judge decides first and the operator is asked only when the judge gives no verdict or has escalated. "Operator" means the judge never sees the ask. For a worker, "asks" means the worker's ask route, `fleet.permissions.mode`, which by default hands an ordinary ask to the main session's judge.

| Action | `default`, operator's session | `yolo`, operator's session | Workers at `default` |
| --- | --- | --- | --- |
| Read, list, search or `data` inside the workspace or a [read-scope exemption](#read-scope) | runs | runs | runs |
| Read, list, search or `data` outside the workspace, on a path no zero-access entry covers | runs | runs | asks |
| Write or edit inside the workspace | runs | runs | runs |
| Typed write or edit that lands strictly inside a [scratch root](#scratch-roots), with no `.git` or `.clio-coder` directory on the way | runs | runs | asks |
| Typed write or edit elsewhere outside the workspace: a new file (`system-modify-confirm`) or a replaced existing file (`outside-file-replacement`) | judge | runs | asks |
| Typed write, edit or artifact on a git control file (`git-control-file`) | judge | runs | asks |
| Typed `git` add or commit, an uncontained bash call naming `git`, `gh`, `glab` or `hub`, or an uncontained `run_script`, after a hook file changed since the operator's baseline (`git-hooks-changed`) | operator | runs | operator under `judge`, denied with nobody attached |
| [Recognized command](#recognized-commands) | runs | runs | runs |
| Contained `bash` or `run_script` call, whatever its recognition | runs | not applicable | not applicable |
| Uncontained command outside the recognized set: no sandbox backend, `safety.sandbox: off`, or `unsandboxed: true` | judge | runs | asks |
| Outward action: `git push` other than `--dry-run`, a code-host, cloud or publishing CLI, a network write, `web_fetch` other than a bodiless GET or HEAD | judge | runs | asks |
| `ask_user` with `exposure: outward` | operator | answered by Clio | not applicable |
| Worktree discard or workspace delete a snapshot undoes | runs after a snapshot | runs | blocked or asks |
| Other former damage-control block, `delete-outside-workspace`, destructive git | judge | runs | blocked |
| Damage-control confirmation rule no snapshot undoes, or a tool confirmation such as `slurm-allocation` | judge | runs | asks |
| Model edit of project settings (`project-settings-confirm`), a shell library change (`library-confirm`), a `configure_clio` apply on fleet routing (`fleet-routing-settings`), plan-scale dispatch | operator | runs | asks |
| Zero-access, read-only, no-write or no-delete path; operator authority rail | blocked | only operator-authored entries block | blocked |
| Yolo floor | blocked | blocked | blocked |

A read-only run is a dispatch restriction, not a level. Reviewer, judge and council roles, `/oracle`, the watchdog verifier, fleet `scope: readonly`, recipes with `capabilityClass: read-only`, and the operator's `--read-only` flag set it. For mediated tools, the registry denies calls other than reads inside the workspace, including skill activation. Dispatch refuses a read-only request on an agent-managed ACP peer that cannot enforce the restriction; subprocess runtimes do not expose per-call registry mediation, and their read-only guarantees vary by runtime.

### Recognized commands

Recognition decides an uncontained command: a worker's command, the main session's command when no sandbox backend exists or `safety.sandbox` is `off`, and a call that leaves the sandbox. A contained command of the operator's session at `default` runs whatever its recognition. A bash command runs without an ask only when every step is recognized. Recognition is conservative. A word the shell would expand (an unquoted `~`, brace or glob, a `$'...'` or `$"..."` word), a substitution, or an option that can write, execute, name an input list or follow links leaves the whole command unrecognized, and the autonomy level decides it: it asks at `default`, where the safety judge reviews the main session's ask first, it runs at `yolo`, and it is denied in a read-only run. The recognized set is:

- **Built-in test runners** with bare-word arguments only (`TEST_RUNNER_COMMANDS` in [policy-engine.ts](../../src/domains/safety/policy-engine.ts)): `npm`, `pnpm`, `yarn` and `bun` with `test`, `run test` or `run test:<name>`; `node --test`; `pytest`; `python -m pytest` and `python -m unittest`; `uv run --no-sync pytest` and `uv run --no-sync python -m pytest` (`--frozen` and `--locked` allowed, `--no-sync` required because a synchronizing `uv run` downloads dependencies); `cargo test`; `go test`; `ctest`; `make test` and `make check`; `ninja test`; `meson test`; `mvn test`; `gradle test` and `gradlew test`. They execute repository-authored code, which is the accepted cost of letting a headless run verify its own work. In an attended main session (TUI or ACP) at `default`, the session's first uncontained test-runner command asks the operator once, whoever wrote the code it runs, whether it runs alone, in a chain, through a `verify` check, or as the host check of an otherwise admitted `dispatch` or `job`; approving it covers test runners for the rest of the session. A contained `bash` or `run_script` test runner owes no such consent, because the sandbox bounds what it writes. A new, resumed or forked session asks again. A headless `clio-coder run` at `default` runs them without asking, and workers and `yolo` are unchanged. Quoting, substitution and operators fall through to the other rails.

  The Python runners (`pytest`, `python -m pytest`, `python -m unittest`, and the two `uv run --no-sync` forms) also accept a leading `PYTHONPATH=<entries>` for a src-layout project, as in `PYTHONPATH=src python3 -m pytest tests`. Every colon-separated entry must be a non-empty relative path made of word characters, `.`, `/` and `-`, with no `..` segment. An absolute entry, a `..` segment, any other leading variable assignment, or the prefix on a runner outside that list leaves the command unrecognized. The prefix is read only on a standalone command, never on a step inside a chain. It adds no reach, because the runner already executes the repository's code from the call's cwd and the relative entries keep the import roots inside it, and a worker that would otherwise be denied the unrecognized form runs the check its task named.
- **Project commands** declared in an approved `.clio-coder/safety.yaml`. An entry with `requireConfirmation: true` asks at `default`, contained or not, and runs at `yolo`.
- **Project scripts** `npm run lint`, `npm run build`, `npm run typecheck` and `npm run ci` pass the safety net but stay unrecognized unless a project command declares them.
- **Read-only inspection** on workspace paths: `cat`, `head`, `tail`, `wc`, `nl`, `ls`, `pwd`, `stat`, `basename`, `dirname`, `realpath`, `readlink`, `echo`, `printf`, `true`, `which`, `cut`, `tr`, `grep`, `egrep`, `fgrep`, `rg`, `find` and `sed -n` with a print-only line script. Each operand is held to the workspace as the `read` tool holds its path, and options that write, execute, read a list file or walk links are refused: `tail -f`, `wc --files0-from`, `ls -R`, `-L` and `-H`, `grep -f`, `printf -v`, `find -exec`, `-delete`, `-fprint` and `-L`, and every GNU long-option abbreviation of those.
- **`rg`** when it searches named regular files, a directory that a bounded walk proves holds no zero-access file (10,000 entries across the whole command, symlinks not followed), `--files` listings, or a pipe with no file operand. It is not recognized while the tool environment names `RIPGREP_CONFIG_PATH`, nor before the login environment has been captured, because a ripgrep config can add `--follow`, `--pre` and `-z`.
- **Git inspection**: plain `git`, optionally with leading `-C <dir>` options that stay inside the workspace, in the inspect class of the shared Git policy ([git-policy.ts](../../src/domains/safety/git-policy.ts)), such as `status`, `diff`, `log`, `show`, `rev-parse`, `rev-list`, `ls-files`, `ls-tree`, `describe` and the listing forms of `branch`, `tag` and `stash`. These can print the history of files already tracked in git. `git grep`, `git blame`, `git annotate` and `git cat-file` are unrecognized, as are helper-invoking flags such as `--ext-diff` and `--output`, and `git diff --check` is recognized only as a standalone command.
- **`cd <workspace directory>`** as a chain step outside a pipeline, when the target and its physical resolution stay inside the workspace and carry no expansion.
- **Chains** of up to 16 recognized steps joined by `&&`, `||`, `;` or `|`, with output redirected only to `/dev/null` or merged with `2>&1`. Every step is checked on its own and the chain takes the strictest verdict.

An uncontained command that hides its content asks even when each word looks harmless. An uninspectable shell script, `$VAR` or interpreter source (`python -c`, `node -e`) asks under rule `bash-hidden-content`, command substitution asks under `bash-command-substitution`, and a bash `cwd` outside the workspace is blocked under `bash-cwd-escape`. None of the three applies to a contained call or at `yolo`.

## Containment at default

Containment is what lets the operator's own session run shell work at `default` without an approval ask for what Clio cannot see or bound in the command text. The OS bounds where the command writes and hides the operator's credentials ([containment.ts](../../src/domains/safety/containment.ts), [main-session.ts](../../src/core/sandbox/main-session.ts)).

### When a call is contained

A call is contained when all of these hold:

- It is a `bash` or `run_script` call of the operator's own main session at `default`. Workers, grants, scheduled command jobs and every other caller are never contained by this sandbox.
- `safety.sandbox` is `auto` or `required` and the backend probe answered: bubblewrap on Linux, `sandbox-exec` on macOS. With no backend nothing is contained and the uncontained rails apply; `required` does not refuse the main session's commands at `default`.
- The call does not carry `unsandboxed: true`. `bash` and `run_script` accept that argument for a command the sandbox broke, for example one that needs credentials or a path outside the writable roots. The call then goes through admission as an uncontained call, so a command outside the recognized set goes to the safety judge.
- The command does not reach outward (`outwardShellReason`): `git push` other than `--dry-run`; the code-host and cloud CLIs `gh`, `hub`, `glab`, `tea`, `aws`, `gcloud`, `gsutil`, `az`, `kubectl`, `helm`, `terraform`, `tofu`, `pulumi`, `firebase`, `vercel`, `netlify`, `wrangler`, `fly`, `flyctl`, `heroku` and `doctl`, and `ssh`, `scp` and `sftp`, in every subcommand; publishing subcommands of `npm`, `pnpm`, `yarn`, `bun`, `cargo`, `twine`, `poetry`, `uv`, `flit`, `hatch`, `gem`, `dotnet`, `nuget`, `mvn`, `docker` and `podman` (`publish`, `upload`, `push`, `deploy`, `login` and their kin); `curl` with a body, an upload or a method other than GET or HEAD; `wget` with a post or body option or `--method`; `http`, `https` or `xh` with a write method; and `rsync` to or from a remote host. The check reads through `timeout`, `nohup`, `nice`, `time`, `stdbuf`, `ionice`, `npx`, `pnpx`, `bunx` and `xargs`. Each of these needs the credentials the sandbox hides, so it runs unsandboxed after the ordinary rails and the judge. A false match only sends the call to the judge.

A backend that is gone by spawn time refuses the command with `sandbox: the main-session sandbox is unavailable (...); the command was not run`, because admission let it run without an ask on the strength of the sandbox.

### The main-session sandbox

The filesystem stays readable. A contained command may write only:

- the workspace;
- the [scratch roots](#scratch-roots);
- the package caches `$XDG_CACHE_HOME` (default `~/.cache`) and `~/.npm`, which are not scratch roots, so deletes there get no scratch-root treatment;
- the git dirs of the repository holding the workspace: its git dir, the common dir a linked worktree's `.git` file and `commondir` lead to, the linked worktrees' git dirs and the submodule git dirs under `modules/`, each bound as a mount of its own so a command cannot rename one aside and plant a forged one. `git commit`, `fetch`, `pull` and `checkout` work.

Inside those roots these stay read-only: the workspace's `.clio-coder`; each scratch and cache root's `.git` and `.clio-coder`; every git dir's hooks directory and its `config`, `config.worktree` and `commondir` files, the `.git` files that point at git dirs, and every directory `core.hooksPath` names, because a write there (a hook, `core.hooksPath`, `core.fsmonitor`, aliases, filter drivers) becomes code that runs later outside the sandbox; the code caches `~/.npm/_npx`, `$XDG_CACHE_HOME/node/corepack`, `$XDG_CACHE_HOME/uv` and `$XDG_CACHE_HOME/pre-commit`, which run later outside the sandbox; and Clio's own config, data, state and cache directories. `~/.local` is not writable, because `~/.local/bin` is on `PATH`. `core.hooksPath` is read from every config scope and include (system, global, repository and worktree), every value counts, and a relative one is resolved against the work tree, so husky's `.husky` and a `.githooks` directory stay read-only; when husky 9 names `.husky/_`, its parent `.husky` counts too. A hooks path at or above the workspace root is not made read-only, since that would freeze the whole workspace. Under bubblewrap an absent hooks directory gets an empty tmpfs (an absent `core.hooksPath` directory only when it sits directly in the workspace root), and an absent `config` or `commondir` file the command creates is removed when the sandbox exits.

The worker sandbox's credential masks apply: `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.azure`, `~/.kube`, `~/.docker/config.json`, `~/.netrc`, `~/.git-credentials`, `~/.npmrc`, `~/.pypirc`, `~/.cargo/credentials`, `~/.config/gh`, `~/.config/hub`, `~/.config/gcloud`, `~/.password-store`, `~/.local/share/keyrings` and Clio's credential store, plus `/run/user/<uid>` and the Docker sockets ([secret-paths.ts](../../src/domains/safety/secret-paths.ts), [worker-process.ts](../../src/core/sandbox/worker-process.ts)). The ssh-agent directories `/tmp/ssh-*` and the session's `SSH_AUTH_SOCK` are masked too and `SSH_AUTH_SOCK` is unset, so a `git push` over SSH from inside fails. The command runs in its own PID namespace and cannot signal host processes. Unlike a worker it sees the host's real `/tmp`, where operators expect benchmark output, and the network stays on because this is the operator's own session.

**Environment.** Because a contained command reaches the network without a judgment, it starts from a scrubbed environment ([env-scrub.ts](../../src/core/sandbox/env-scrub.ts)). A variable is removed when its name carries `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `PASSPHRASE`, `ASKPASS`, `API_KEY`, `ACCESS_KEY`, `PRIVATE_KEY`, `CREDENTIAL`, `SESSION_KEY`, `COOKIE` or `CONNECTION_STRING`, carries `AUTH` as a word part (not `AUTHOR`), ends in `KEY`, `KEYS`, `PASS`, `PWD` or `PAT`, starts with `AWS_`, `PYPI_`, `TWINE_` or `VAULT_` (the AWS region and profile variables stay), is `KUBECONFIG` or `NETRC`, or names a key variable a configured target reads (`auth.apiKeyEnvVar`). A variable whose value is a URL with an embedded `user:password`, a connection string with a password or account key, or a private key block is removed whatever its name. `safety.sandboxPassEnv`, read only from the operator's user settings, lists names to keep. The scrub runs on the environment handed to the sandbox executable, because bubblewrap's `--unsetenv` would leave the values readable in `/proc/1/environ`. Worker sandboxes scrub the same way. A command that leaves the sandbox (`unsandboxed: true` after the judge) and every command at `yolo` keep the environment they had.

**Secret files.** Secret files under the workspace and the scratch roots are masked ([secret-files.ts](../../src/core/sandbox/secret-files.ts)): bubblewrap binds `/dev/null` over a file, which its `nodev` turns into a refused open, and an empty tmpfs over a directory, and Seatbelt denies reading either. The names are the ones the typed read tools refuse (`WORKSPACE_SECRET_PATHS` in [secret-paths.ts](../../src/domains/safety/secret-paths.ts)), matched at any depth: `.env` and its variants, `*.env`, service-account and credentials JSON files, `*.key`, `*.p12`, `*.pfx`, Terraform state, `.terraform/`, `.vercel/`, `.netlify/`, `.supabase/`, `.git-credentials`, `.netrc`, `.pypirc`, `id_rsa` and the other SSH key names, Kerberos `krb5cc_*` caches, plus copies of the home credential stores. A `.pem` is masked only when it holds a private key, and a project `.npmrc` only when it carries a literal registry token. Templates such as `.env.example`, `.sample` and `.template` files stay readable, and so does a tracked file with no uncommitted change, because its content is readable through git objects anyway and masking it would break `git add -A`. Dependency, build and virtualenv trees (`node_modules`, `.venv`, `venv`, `target`, `dist`, `build`, `site-packages` and any directory holding `pyvenv.cfg` or `conda-meta`) are not searched. Files are found through git's listing, or a walk six levels deep and 20,000 entries wide outside a repository; a workspace's result is reused for 10 seconds or until its top directory changes, a scratch root's for 30 seconds, and at most 512 masks are added. A worker's sandbox masks the same names in its worktree and checkouts.

**Unix sockets.** Linux lets a process connect to a socket on a read-only mount, and a terminal multiplexer's control socket (Herdr, tmux), an X11 display or a daemon's control socket runs commands outside the sandbox ([unix-sockets.ts](../../src/core/sandbox/unix-sockets.ts)). Every bubblewrap sandbox Clio launches, for the main session at `default`, workers, MCP servers and the extension runtime, therefore loads a classic BPF seccomp filter that makes `socket(AF_UNIX)` and `io_uring_setup` fail with `EPERM`, for x86_64 (with the x32 bit masked), i386, aarch64 and arm, since a 64-bit process can enter the 32-bit ABI. `socketpair`, pipes, TCP and Node's IPC channels keep working. The program is written once under `<stateDir>/sandbox/` and handed to bubblewrap on fd 9. The Seatbelt profile denies connecting to and binding Unix sockets, which has not been run on macOS. Where bubblewrap cannot load the filter, each launch masks the user-owned sockets it finds in the home directory, the temp roots, the scratch roots and the workspace, up to 256, and abstract-namespace sockets and sockets created after the launch stay reachable. `safety.sandboxUnixSockets: allow`, read only from user settings, turns the refusal off.

Tools that need a local Unix socket fail inside the sandbox with `Operation not permitted`: the `tsx` CLI's IPC server, Python's `forkserver` start method (the Linux default from Python 3.14), any program that listens on a socket path, local database sockets, the Docker daemon, and X11 and D-Bus clients. In the main session the model is told to rerun such a command with `unsandboxed: true`, which the safety judge reviews; a dispatched worker names the command in its result.

Typed tools agree with the sandbox on these git control paths. In the operator's session at `default`, a `write`, `edit` or `artifact` call asks under `git-control-file`, so the safety judge decides it against the operator's intent, when its target, as named or as resolved through links, is a git control path. That is the union of two sets. By name alone, with no filesystem access and in any repository, including one created mid-run: a `.git` pointer file, and below any `.git` segment `hooks/**`, `config`, `config.worktree`, `commondir`, `info/attributes`, a linked worktree's `config.worktree`, `commondir` or `gitdir`, and a submodule git dir's hooks and config under `modules/`. By resolution: the workspace repository's set that the sandbox keeps read-only, linked worktrees, submodules and every `core.hooksPath` directory included, whether or not the file exists yet. The resolved set is cached and refreshed after a git control write, a shell command naming `git config`, `init`, `clone`, `worktree` or `submodule`, `hooksPath`, husky or a package install, and any `run_script`. The path policy still blocks `.git/config` outright as a zero-access path. A worker at `default` asks for the same paths too; see [Workers at each level](#workers-at-each-level). Grants and `yolo` are unchanged.

A failed contained command whose output shows a refused write (`EROFS`, `EACCES`, `EPERM`) gets one result line naming the writable roots, suggesting a rerun with `unsandboxed: true`, and pointing at `safety.scratchRoots` for a directory scripts should always write. `clio-coder doctor` reports the case that applies in its `shell sandbox` row: contained with the backend, the writable roots, the number of masked secret files and the Unix-socket treatment, or uncontained with the reason. The row warns when the secret-file search stopped at its limit or when sockets fall back to masks.

### Git hook drift

A git hook runs with the privileges of whoever runs git next, outside the sandbox, and some routes to plant one are not closed by name and path rules: a separate git dir created mid-run, a nested repository's hooks path, a hooks directory created below the workspace root, a config changed outside Clio. So the main session also watches what git would run ([git-hooks-fingerprint.ts](../../src/core/sandbox/git-hooks-fingerprint.ts), [hook-drift.ts](../../src/domains/safety/hook-drift.ts)).

At session start Clio fingerprints every hook file (kind, executable bit, size, SHA-256 of the first 4 MiB, first line) of the workspace repository and of each repository a bounded walk finds inside the workspace, covering default hooks directories, every `core.hooksPath`, linked worktrees and submodules. The fingerprint also covers every git config value that makes git run a command, read with `git config --list --show-origin` in every scope (system, global, repository, worktree and includes) for each of those repositories: `core.fsmonitor` (unless a boolean), `core.sshCommand`, `core.pager`, `core.editor`, `core.askPass`, `core.gitProxy`, `core.alternateRefsCommand` and `core.hooksPath`; `sequence.editor`; `diff.external` and each `diff.<driver>.textconv` and `.command`; each `filter.<driver>.clean`, `smudge` and `process`; each `merge.<driver>.driver`; `credential.helper`; `gpg.program`, `gpg.<format>.program` and `gpg.ssh.defaultKeyCommand`; shell aliases (`alias.*` starting with `!`); `uploadpack.packObjectsHook`; `remote.<name>.uploadpack`, `receivepack` and `vcs`; `pager.<command>` set to a program; `trailer.<token>.command` and `cmd`; a `submodule.<name>.update` starting with `!`; `difftool.<tool>.cmd` and `mergetool.<tool>.cmd`; and `interactive.diffFilter`. An empty value runs nothing and is not counted. A repeat check re-reads only directories whose modification time moved, and lists config again only when a file it read moved. At `default`, before a typed `git` add or commit, an uncontained bash call naming `git`, `gh`, `glab` or `hub`, or an uncontained `run_script`, a hook file or executable config value added or changed since the baseline turns the call into an operator-only ask under `git-hooks-changed`. The safety judge never decides it, a headless run denies it, and an unanswered card times out to a denial. The card names the changed files; the operator's allow runs the call and accepts exactly those files as shown, so a later change asks again. An approved or judge-allowed `git-control-file` write refreshes the baseline for the file it wrote. A removed hook is not drift.

The first detection of each change adds a transcript notice, `[safety] git hook files or executable git config changed during this session: ...`, and the exit summary gains a `Git hooks` line listing what changed during the visit, such as `changed .git/hooks/pre-commit · added core.fsmonitor in .git/config`, so the operator can review before running git in their own terminal. Under `fleet.permissions.mode: judge`, a worker's git call after drift goes to the operator instead of the judge, and is denied with nobody attached. The worker sandbox keeps every hooks directory inside a writable root read-only. Yolo is unchanged.

The guard sees hook files and the executable config keys above; a program git runs by another route, such as an attribute-selected driver whose config value did not change, is not fingerprinted. Repositories more than 12 directory levels deep, beyond the walk's 4,000 directories, or inside `node_modules` are not covered. A contained git command is not checked, because its hooks run inside the sandbox, and git the operator runs outside Clio is never intercepted.

### Clio's own git

Clio also runs git itself, outside any sandbox and without a tool call: task worktrees, landing worker results, ref updates, footer and status probes, snapshot plumbing, library sync, and the diffs behind run records and views ([internal-git.ts](../../src/core/internal-git.ts), [internal-git-policy.ts](../../src/domains/safety/internal-git-policy.ts)). Every such call is built by `internalGitArgv` and always carries `--no-optional-locks`, `core.fsmonitor=false` and `log.showSignature=false`, so a read never runs an fsmonitor command, a signature check or the `post-index-change` hook. `diff`, `log` and `show` also carry `--no-ext-diff` and `--no-textconv`, so `diff.external` and textconv drivers never run, and snapshot plumbing always runs with hooks off.

Clio's hook-running operations (worktree add, checkout, merge, commit, ref updates such as a branch delete, fetch, push and library sync) ask the drift guard first. A repository outside the workspace gets a guard of its own whose baseline is Clio's first operation there. Without drift the operation runs as the repository configures it. After drift at `default` it runs with `core.hooksPath` pointed at an empty directory under Clio's state directory, and every changed executable key set to a value that runs nothing (`core.fsmonitor=false`, `core.sshCommand=ssh`, `core.pager=cat`, an empty credential helper or filter command, a merge driver that fails so Clio aborts the merge, signing off, and the like). Clio's read-only git (status, diff, ls-files, hash-object) gets the same per-key overrides. Only changed keys are overridden, so drivers present at the baseline, such as git-lfs filters, keep working. A key no command-line value can turn off (`core.gitProxy`, `remote.<name>.vcs`, `uploadpack.packObjectsHook`, or any key whose subsection contains `=`) stays in force for a hook-running operation, which the notice says, and makes Clio skip its own status and diff probes in that repository while the drift stands. The probes resume once the change is reverted or the operator approves it on the agent's next git command.

The transcript notes each drift Clio's own git met once, and the exit summary gains an `Internal git` line such as `git worktree add without hooks (added .git/hooks/post-checkout)`, with the outcomes `without hooks`, `with changed config overridden`, `skipped` and `under yolo with changes`. At `yolo` Clio's own git runs as configured, and the drift is still recorded in the exit summary. Git that Clio runs on a remote fleet node is unchanged.

### Scratch roots

The built-in scratch roots are `$TMPDIR` (through `os.tmpdir()`, while it passes the checks below), `/tmp`, `/var/tmp`, `/private/var/tmp` and, on macOS, `/var/folders` ([scratch-roots.ts](../../src/domains/safety/scratch-roots.ts)). `safety.scratchRoots` adds absolute directories from the operator's own settings file; a project layer value is ignored with a layer issue. A scratch root is writable inside the main-session sandbox, and a delete that lands inside one is judged at `default` as one inside the workspace is. A typed `write` or `edit` whose target, resolved through links, lands strictly inside a scratch root with no `.git` or `.clio-coder` directory between the root and the target is a plain write at `default`: no `system-modify-confirm` or `outside-file-replacement` ask and no safety judge call. The floor, path policy, authority rails and write roots still judge the target. Workers, grants and `yolo` are unchanged.

Validation rejects a relative path, `/`, `$HOME` or an ancestor of it, a root inside a system tree (`/etc`, `/usr`, `/bin`, `/sbin`, `/lib` and its kin, `/boot`, `/root`, `/dev`, `/proc`, `/sys`, `/run`, `/snap`, `/var`, `/opt`, `/srv`, `/nix`, `/private`, `/cores`, `/System`, `/Library`, `/Applications`) other than the temp trees (`/tmp`, `/var/tmp`, `/private/tmp`, `/var/folders`, `/private/var/folders`), and `/mnt`, `/media` and `/Volumes` with the mount roots directly inside them. A root that resolves through a link to a rejected place, or that contains the workspace, is dropped at run time, and `clio-coder doctor` warns about it.

### What containment replaces

A contained call needs no ask for these rails: the unrecognized-command autonomy ask (`bash-unrecognized` and the other unrecognized forms), `bash-hidden-content`, `bash-command-substitution`, `bash-hidden-quoting`, `system-modify-confirm` (admitted as `contained:system-modify-confirm`), `bash-cwd-escape` (a `cwd` outside the workspace runs, and `run_script` accepts a script or `cwd` outside it), and the session's test-runner consent. Execute, system-modify and destructive action classes are admitted.

Containment does not lift anything else. The floor, write roots, path policy and authority rails still block; the damage-control re-sort, authored confirmation rules, a project command's `requireConfirmation`, `library-confirm`, `project-settings-confirm` and `delete-without-snapshot` still ask.

## Workspace snapshots and /rewind

Recoverability is the layer that lets an undoable action run without an approval ask ([workspace-snapshots](../../src/domains/workspace-snapshots/index.ts)). With `safety.snapshots` at `auto` (the default; `off` takes none) and a Git work tree, the main agent's registry writes the work tree to a snapshot commit before:

- the first mutating call of each turn: a write, execute, system-modify or destructive call, other than bash recognized as read-only inspection, `web_fetch` and `configure_clio`;
- every destructive call, every bash delete, every git discard (`checkout` with a pathspec, `.` or `--force`, `restore`, `clean`, `reset --hard`, `--merge` or `--keep`, `stash drop`, `clear` or `pop`), every branch delete (`git branch -d`, `-D` or `--delete`, reason `git-ref-delete`), and every `git reset` that names a commit other than `HEAD` (reason `git-ref-move`), each with a snapshot of its own;
- every call admitted because a snapshot undoes it.

This happens on every surface (TUI, ACP and headless) and at both levels. Dispatched workers take no snapshots.

A snapshot captures tracked files and untracked files that are not ignored, in a private per-session index under `<stateDir>/snapshots/<session>/`, and stores the commit at `refs/clio-coder/snapshots/<session>/<n>`, which Git keeps in the common directory of a linked worktree ([store.ts](../../src/domains/workspace-snapshots/store.ts)). Ignored files, untracked files over 16 MiB and nested repositories are skipped and recorded. The operator's index, HEAD and branches are never touched, and the commit carries a fixed Clio Coder identity.

A snapshot also pins refs a destructive Git command can lose without touching a file ([pins.ts](../../src/domains/workspace-snapshots/pins.ts)). Every snapshot pins HEAD and each stash entry, up to 64 with the rest named in the snapshot's note, and a branch delete also pins the tips of the local branches it names. A remote-tracking delete pins nothing, because the next fetch brings those refs back. The pins live under `refs/clio-coder/snapshots/<session>/pins/<n>/` and are written in one `update-ref` transaction beside the tree ref, so `git gc` keeps those commits. A snapshot of an unchanged tree is reused only when the latest snapshot already pins every current ref. Each session keeps its 50 newest snapshots, and a session's first snapshot prunes the refs, pins and state of sessions idle for 14 days.

A snapshot or pin that cannot be taken never holds an ordinary call: the call runs and its result carries `no snapshot: <reason>`, or `snapshot #<n>: <detail>` when the files were captured but a ref was not pinned. A call admitted only because a snapshot would undo it is refused instead, under reason code `snapshot-required`, when no snapshot could be taken or a ref the call destroys or moves could not be pinned, and the model is told to take a route that discards nothing or record the open decision.

`/rewind` in the TUI lists the session's snapshots newest first with how many files each differs from the workspace by. `Enter` previews what a restore would change before anything is written. Confirming takes a pre-rewind snapshot, so the rewind itself can be rewound, then restores modified and deleted files and removes files that exist now but are absent from the snapshot. Ignored files are left alone, and differences a rewind cannot settle are listed as kept. A rewind restores files only and never changes the index, HEAD or branches. The snapshot details list its pinned refs (HEAD with its branch, each stash entry, each pinned branch), and the preview marks each one still in place, moved since, gone or not checked, with the command that brings a moved or deleted ref back: `git branch`, `git branch -f`, `git reset`, `git switch --detach` or `git stash store`. `/rewind` prints these commands and never runs them; after a restore, its notice repeats them for refs that moved or are gone. `/rewind` waits for a running turn to finish or be stopped. `/tree` rewinds the conversation; `/rewind` rewinds files.

## Damage control at default

The operator's own session at `default` re-sorts the [damage-control rules](#damage-control-rules) and the delete judge, which still block for workers and every other caller ([policy-engine.ts](../../src/domains/safety/policy-engine.ts)):

| Outcome | Rules |
| --- | --- |
| Run after a snapshot (`snapshot-recoverable`) | Worktree discards: `git reset --hard` (`git-reset-hard`, `git-reset-hard-head`), `git checkout -f`, `git checkout .` and the other whole-tree checkouts (`git-checkout-force`, `git-checkout-dot`, `git-checkout-discard-all`), `git restore .` (`git-restore-discard-all`), `git stash drop` (`git-stash-drop`, whose dropped entry the snapshot pins), and `git clean` without `-x` or `-X` (`git-clean-force-directory`), since a snapshot leaves ignored files out. Deletes the delete judge places inside the workspace or a scratch root, including build output and dependency trees, which this session may delete but never writes into. A lone discard or `rm`, `rmdir` or `unlink` runs under `snapshot-recoverable`; in a chain the same step follows the other rails and still gets its snapshot. With no Git work tree or `safety.snapshots: off`, a git discard follows the next row and a workspace delete asks under `delete-without-snapshot`. |
| Judge asks | Every other former hard block: force pushes, `git clean -x`, `git stash clear`, `git reflog expire`, `git gc --prune=now`, `git filter-branch`, `sudo rm`, `rmdir --ignore-fail-on-non-empty`, `find -delete` and `rsync --delete` the snapshot cannot cover, `shred`, `chmod 777` and recursive `chmod` or `chown`, `kill -9 -1`, `killall -9`, `pkill -9`, clearing shell history, `curl` or `wget` piped to a shell, writes to system roots through redirects or `tee`, cloud deletion commands, SQL `DROP`, `TRUNCATE` and `DELETE` without a `WHERE`, `delete-outside-workspace`, and destructive git that no rule names. Each carries its own reason code (`damage-control:<rule>`, `classification:git_destructive`). Authored confirmation rules no snapshot undoes ask the same way: `git branch -D`, whose branch tip the snapshot before it pins, remote branch deletes, `gcloud iam policies`, SQL `DELETE` by id, `truncate -s 0` and `:>`. |
| Still block | The [yolo floor](#the-yolo-floor), path policy, authority rails, write roots and an invalid approved policy. |

A former block never asks on top of an operator-only ask that already holds the call; its reasons join that ask's instead. An operator's approval of the exact call answers the deferred ask.

## The safety judge

The safety judge is the model-based reviewer at the heart of `default` ([safety-judge.ts](../../src/domains/safety/safety-judge.ts), [safety-judge-host.ts](../../src/entry/safety-judge-host.ts)). Whatever would park for an operator approval in the main session at `default` is first reviewed against the operator's own words. It runs on every main-session surface: the TUI, ACP clients including the GUI, and headless `clio-coder run`. It never runs at `yolo`, where nothing asks. Under `fleet.permissions.mode: judge` it also answers dispatched workers' ordinary asks; see [Workers at each level](#workers-at-each-level).

### What the judge reads

The judge is reasoning-blind by construction. It reads only:

- the operator's typed messages on the session's active path, oldest first: the newest whole up to 24 KiB, then older messages while they fit 6 KiB, at most 12. The path runs through the turn the judged call serves even when the session leaf has not caught up with it, while a branch the operator left with `/tree` stays out; a worker's ask uses the session's live leaf, and when the session tree cannot be read the newest ledger message stands in as the leaf. A continuation nudge Clio synthesized is skipped, and injected reminders and expansions are stripped;
- the proposed call: the tool, its action class, the rule that asked, why Clio asked, the policy reason, the consequence sentences Clio computes for the card, and, for a worker's ask, a line saying a dispatched worker made it;
- the call's arguments with secrets redacted, inside a per-call random tag so content cannot close the data block early: a bash command up to 16,000 characters with its `cwd`, a `write` path with its size and a 1,500-character head, an `edit` path with its edits up to 1,500 characters, and any other tool's arguments as JSON up to 4,000 characters.

It never sees assistant text, thinking, tool results, project instruction files, a dispatch task or a worker transcript, so content the agent read cannot argue past it. Text inside the call that claims an approval has no authority.

### Rules and verdicts

The judge blocks a call that would do one of these unless an operator message explicitly asks for that specific action: `destroy-data` outside the workspace and scratch roots, `publish` (push, publish, deploy, issues or pull requests, posts), `rewrite-history`, `exfiltrate` workspace data or secrets to an unrelated host, change `shared-config` (system or shared configuration, other users' files, cron or systemd units, shell rc files), weaken `clio-safety`, kill a `foreign-process`, mass `cloud-delete`, or run `remote-code` fetched from the network. It allows `operator-named` actions, `read`s anywhere, installing a declared `dependency`, work in the `scratch` roots, and a `task-local` action that plainly serves the stated task. A request about one target does not authorize the same action on another, and a call it cannot read is blocked with rule `unclear`. It also reads a reach ladder (`contained`, `local`, `broad`, `irreversible`), the operator's `safety.judge.environment` lines, and `safety.judge.allow` and `safety.judge.deny` lines as extra `operator-allow` and `operator-deny` rules. That static prefix changes only when the operator edits `safety.judge`, so a provider's prefix cache holds across reviews.

The judge answers one JSON object, `{"verdict":"allow"|"block","rule":"...","reason":"..."}`, within 400 output tokens.

- **Allow**: the call runs with no card, and its `tool.decided` record carries `safety-judge:allow`.
- **Block**: the model reads the refusal `Clio's safety judge blocked this <tool> call (rule <rule>): <reason>`, is told not to retry the call or a reworded form of it, and is pointed at the workspace and scratch roots or at recording the open decision. Its `tool.decided` record carries `safety-judge:<rule>`, and a hidden ledger note records it.
- **No verdict**: no route (no judge target and no chat route), a 30-second timeout, a cancelled call, a route error or an unreadable answer. The call parks exactly as it would without a judge: the card carries the judge's reason for handing it over when attended, and a headless run denies it. No verdict never counts as a block.

Three consecutive blocks or twenty blocks in one session escalate: the next eligible call goes to the operator unjudged, with a card that says why, and a worker's ordinary asks are denied. An operator approval of any parked call turns review back on and resets both counts. Worker and main-session blocks share the counts.

### Asks only the operator answers

The judge never sees these: a harness call; `ask_user` and `configure_clio`, the operator's own channel and Clio's own settings tool; a worker escalation or a worker's operator-authority ask; a plan-scale dispatch approval; a session-consent or worker Git-hooks ask; and asks under the rules `session-code-consent`, `project-settings-confirm`, `fleet-routing-settings`, `library-confirm`, `clio-owned-state` and `git-hooks-changed`.

### Route and settings

`safety.judge` (`enabled`, `target`, `model`, `environment`, `allow`, `deny`) is read only from the operator's user settings and at every review. A null `target` asks the session's chat route; a null `model` asks the chat model, or the judge target's default model when a target is set. The round goes through System One's one-shot port, holds a foreground slot on its endpoint, and is refused like any model request when the session's information-flow labels do not admit the judge's destination. With `enabled: false` every ask parks as it would without a judge. Every review journals a `safety.judged` record. Its context names the session, turn and tool call, and its payload holds the tool, action class, worker run id, asking rule, verdict (`allow`, `block`, `none` or `escalated`), rule, latency, route target and model, the cause of a missing verdict (`noVerdict`), and `operatorMessages`, the number of operator messages the judge's prompt carried. The judge's reason prose stays out of the journal. `operatorMessages` is absent when no prompt was built, such as an escalated call or one with no route, and a `0` shows the judge saw no operator request at all.

## Unattended resolution

An operator who starts a long job and walks away comes back to a finished turn, not a parked card ([unattended.ts](../../src/domains/safety/unattended.ts)). `safety.unattendedAfterSeconds` (default `300`, user layer only, `0` waits forever) bounds the wait of a main-agent approval card and an `ask_user` round in the TUI. Each reads the value when it starts waiting.

- A permission card nobody answers is denied, never approved, and the turn continues. The model reads that the operator did not answer within that window, that the call did not run, and that it should take a route that needs no approval or record the open decision. An identical retry later in the turn is refused without parking again. Its `approval.resolved` record carries `decidedBy: unattended`.
- An `ask_user` round takes each unanswered question's first, recommended option. A free-text question proceeds on the model's best judgment, and an outward question resolves to not approved. Answers the operator committed before the window closed stay theirs. The model is told which options Clio chose and to state them as assumptions, the decision board records them as Clio's decisions with the options passed over, and a choice Clio made never approves a `Carry out this plan?` question.
- The card and the interview show a countdown. Any key the operator presses stops it for good, and calls queued behind the card start their window again.
- The exit summary gains an `Unattended` line, such as `2 questions auto-resolved · 1 permission ask timed out and denied`.

ACP clients, the GUI, headless runs and worker escalations are unchanged: a worker escalation keeps `fleet.permissions.escalation.timeoutMs`. Harness cards and settings confirmations never time out.

## Yolo

Yolo is the operator's skip-permissions mode for long unattended jobs. The main session never stops for an approval or a question ([policy-engine.ts](../../src/domains/safety/policy-engine.ts), [yolo-floor.ts](../../src/domains/safety/yolo-floor.ts)).

### The yolo floor

The floor is a short list of actions no coding task needs and nobody can undo. It holds at both levels: the operator's own session meets it first at `default` too, so no judge can allow it, and a worker under an inherited yolo meets it as well. Workers at `default` meet the ordinary safety net, whose damage-control and path rules block most of the same commands. A floor hit is a hard block returned to the model with its reason, and never parks. Its rule ids:

| Rule id | Blocks |
| --- | --- |
| `rm-home-or-root` | The damage-control pack rule for `rm` of `/`, the home directory or everything in either. |
| `mkfs-any`, `yolo-floor-mkfs` | `mkfs` and its variants, `mke2fs` and `newfs`. |
| `yolo-floor-wipefs` | `wipefs`. |
| `dd-of-dev`, `yolo-floor-block-device` | Writes straight to a block device through `dd of=`, a redirect or `tee`. |
| `fork-bomb`, `yolo-floor-fork-bomb` | A function that pipes itself into itself in the background. |
| `yolo-floor-delete-target` | `rm`, `rmdir` and `unlink` however wrapped, `find -delete` and `find -exec rm` by their roots, `rsync --delete` by its operands, and `shred`, when a target is `/`, the home directory or an ancestor of it, or lies in a system tree (`/bin`, `/boot`, `/dev`, `/etc`, `/lib` and its kin, `/proc`, `/sbin`, `/sys`, `/usr`, `/var`, `/private/etc`, `/private/var`) other than `/var/tmp` and `/var/folders`. A workspace inside a system tree, such as `/usr/src/app`, keeps everything strictly inside it out of the system-tree judgment. |
| `clio-owned-state` | A write or delete into Clio's own config, data, state or cache directory, which hold settings, user skills, credentials and workspace trust records, however a command spells or reaches it. |
| `trust-authority` | A workspace trust grant made from a tool call (`clio-coder config trust`). |
| `yolo-floor-clio-credentials` | A read of Clio's own credential store or its lock, or a shell word naming either or the config directory that holds them, unless every step only lists names (`ls`, `stat`, `du`, `test`). |

The floor reads the command text, its ANSI-C and locale-decoded forms, each segment, and every directory a literal `cd` can leave the shell in; text inside an inert quoted argument does not count. It also reads each shell script the call runs by literal path line by line: `run_script` with the `bash` or `sh` interpreter, and `bash x.sh`, `sh x.sh` or `bash < x.sh`, following `source`, `.`, `bash`, `sh` and `exec` up to three levels within 256 KiB. Here-document bodies and comments are data. A script it cannot read runs. An interpreter that deletes through its own API, or a path built at run time, is not seen, which is the reach of any skip-permissions mode.

### Operator rules and ceilings

Besides the floor, yolo keeps two things:

- **Operator rules.** The path entries of an approved `.clio-coder/safety.yaml` (`zeroAccessPaths`, `readOnlyPaths`, `noWritePaths`, `noDeletePaths`), judged alone without the built-in defaults, and a bash read of one of its zero-access entries. While the file carries any such entry it is read-only too, because an edit would drop its approval and every rule in it. These block under `operator-rule:<reason code>`, such as `operator-rule:path-policy:zeroAccessPaths`.
- **The run's ceilings.** Write roots (`write-root`), an approved policy that no longer parses (`project-policy-invalid`), an empty bash command, an invalid `verify` working directory, a read-only run, the turn's tool scope, an armed skill's tool surface, and `safety.sandbox: required` on a host with no backend (`yolo-sandbox-required`, which refuses scripts).

Everything else is admitted, including the built-in zero-access and read-only paths such as `.env` and `~/.ssh/`, project settings, project skill trees, library changes, fleet routing applies, plan-scale dispatch, outward actions and every damage-control rule outside the floor. Information-flow refusals of mediated outbound tool calls do not hold either; see [Information flow](#information-flow).

### Sandbox, questions and turns

Yolo runs commands unsandboxed. Only `safety.sandbox: required` keeps a sandbox, and only for scripts: a bash command that runs a script file, and every `run_script`, then runs in the [main-session sandbox](#the-main-session-sandbox) when a backend exists and is refused when none does. Under `auto` the OS sandbox serves dispatched workers only.

`ask_user` resolves at once without reaching the surface: each question takes its first option, an outward question included, and a free-text question proceeds on the model's judgment. The decision board records each choice as Clio's decision. The yolo prompt tells the model the operator is away by contract, to take reasonable defaults, never to wait for an answer, and to state every assumption in its final reply. The turn-ending contract renders a yolo variant that ends turns `Done` and stops a requested plan at its assumptions instead of an approval card.

Workspace snapshots and the telemetry journals stay on at `yolo`, so `/rewind` can still restore files.

### Turning yolo on

The first interactive activation, from the leader key, `/settings`, or a session started with `yolo` through `--autonomy yolo` or the user settings, shows a one-time acceptance card. Only an explicit accept records `safety.yoloAccepted: true` in the operator's user settings and switches; a session started at `yolo` holds at `default` until then. Headless `--autonomy yolo` and an ACP client's mode choice count as acceptance and write nothing ([yolo-activation.ts](../../src/interactive/yolo-activation.ts)).

Yolo is refused for an effective uid 0 outside a detected container ([yolo-host.ts](../../src/core/yolo-host.ts)). Container evidence is the `container` environment variable, `KUBERNETES_SERVICE_HOST`, `/.dockerenv`, `/run/.containerenv`, or a `/proc/1/cgroup` naming docker, kubepods, containerd, lxc or podman; `CLIO_CODER_SANDBOXED=1` attests a sandbox the detection missed. Windows has no effective uid and is never refused. An interactive session that would start at `yolo` starts at `default` with the refusal as a notice, a toggle shows it as a warning, headless `clio-coder run --autonomy yolo` exits 2, an ACP mode change fails with `yolo_refused`, and any other path to `yolo`, such as a hot-reloaded settings file, resolves to `default`.

## Workers at each level

Workers inherit the main session's mode inside their own permit and OS sandbox.

- **At `default`.** A worker's admission is the deterministic [safety net](#the-safety-net): no containment relaxation, no damage-control re-sort, no snapshot, and reads outside the workspace ask. Its asks follow `fleet.permissions.mode`, whose default `judge` hands a native local worker's ordinary (main-authority) ask to the main session's safety judge in the orchestrator. The judge reads the operator's messages and the worker's redacted call, labelled as a worker's call, never the dispatch task or the worker transcript. An allow grants the call once, inside the worker's permit and OS sandbox. A block, no verdict, an escalated judge or a judge that is off denies it, and a denied execute ask counts toward the worker's [refusal limit](worker-dispatch-mechanics.md#worker-refusal-limit). Operator-authority asks are never judged: attended they reach the operator's card, and headless the worker denies them. A worker's typed `write`, `edit` or `artifact` call on a git control file of its repository (the shell sandbox's set for the worker's cwd, linked worktrees included) is a main-authority ask under `git-control-file`, routed by `fleet.permissions.mode` like any ordinary ask: `judge` sends it to the safety judge, `deny` denies it, and a main grant runs it. The paths are matched by name in any repository, a repository the worker creates mid-run included, and against the resolved set of its cwd repository, `core.hooksPath` directories included; the typed `git` tool is unchanged. Under `judge`, a worker's git call after a hook file changed goes to the operator; see [Git hook drift](#git-hook-drift). A worker's destructive git stays blocked.
- **At `yolo`.** A mediated, non-read-only worker whose recipe and task do not declare `asks: deny` or `asks: fail` gets the operator's yolo for every action class (`executeAutonomy: yolo` on its permit). Only the floor, operator rules and its dispatch ceilings (read-only, tool scope, write roots, skill surface) refuse its calls, its commands stay in the worker OS sandbox, and its prompt carries the `safety.yolo-worker` fragment. A read-only or unmediated worker, or one whose recipe or task declares `asks: deny` or `asks: fail`, stays at `default`. See [Worker permits](#worker-permits).

`judge` runs as `deny` at `yolo`, when `safety.judge.enabled` is false, and where no judge can answer: claude-sdk, ACP and subprocess runtimes, remote placements, the fleet CLI and `clio-coder run --agent` ([grant-authority.ts](../../src/domains/dispatch/grant-authority.ts)).

## Headless runs

A headless `clio-coder run` has nobody attached.

- At `default` the main session gets containment, snapshots and the safety judge like any other surface. An ask the judge blocks returns the judge's refusal. Every operator-only ask (plan-scale dispatch included), and every ask the judge leaves without a verdict, is denied with `clio-coder run cannot confirm permission requests; rerun interactively to approve this action.`, followed by the rule, the cause, `This call was denied; no approval is pending.` and, for an unrecognized command, the recognized form to use. The session prompt says approval-required calls are denied. `ask_user` is not registered.
- `yolo` comes only from the run's own `--autonomy yolo`. A `settings.yaml` that sets `yolo` does not carry over; the run starts at `default` and says so on stderr.
- Workers it dispatches at `default` keep the `judge` route, because the judge answers without an operator; their operator-authority asks are denied.

## The safety net

The safety net is the deterministic part of admission. Workers, grants, scheduled command jobs and the other callers meet it as written. The operator's own session meets it with the changes described in [Containment at default](#containment-at-default) and [Damage control at default](#damage-control-at-default) at `default`, and only its floor, ceilings and operator rules at `yolo`. The policy engine checks a call in this order, and the first block wins:

1. Write-root confinement. When a run declares `write_roots`, a write outside them is blocked, and so are commands and dispatch, which could write anywhere. A native worker whose commands run under the OS sandbox (`safety.sandbox` not `off`, a usable bubblewrap backend, a local HTTP runtime, no `fleet.nodes`) keeps `bash`, `verify` and `run_script` because the sandbox binds their writes to the roots. Dispatch stays blocked.
2. Damage-control blocks from [damage-control-rules.yaml](../../damage-control-rules.yaml), any `git_destructive` command that no ask rule covers, and the delete-target rule below.
3. An approved `.clio-coder/safety.yaml` that is invalid. Execution tools fail closed until it is fixed, at both levels.
4. Operator authority. A tool cannot grant workspace trust, change Clio Coder's `settings.yaml` or the workspace trust records, or change installed skills, plugins and extensions outside the operator CLI (`skill-authority`).
5. Path policy. Zero-access paths, such as `.env`, `~/.ssh/`, `*.pem`, `credentials.yaml` and `.git/config`, are neither read nor written, and a bash command that names one is blocked. Read-only paths, such as `.clio-coder/safety.yaml`, `.clio-coder/verifiers.yaml`, installed resource directories, system directories, shell rc and history files, build output (`dist/`, `build/`, `target/`), dependency trees (`node_modules/`, `.venv/`) and minified bundles, are never written. The operator's own session at `default` may delete build output and dependency trees, but still never writes into them.
6. Confirmation rails. A damage-control ask rule, `outside-file-replacement`, `project-settings-confirm` and `bash-hidden-quoting` ask. Library changes, system changes and the ordinary command rails ask too. A library change is a `clio-coder library` `install`, `import`, `update`, `remove`, `enable`, `disable`, `pin`, `register`, `sync`, `push` or `remote` run through a shell (reason `library-confirm`); a `--dry-run` of `install`, `import`, `update`, `enable`, `disable` or `remove` writes nothing and never asks.

The registry then applies the read-only restriction, the turn's allowed tools and any skill's tool narrowing, and last the autonomy mapping.

Paths are judged after links and a physical `..` are resolved, so a link cannot carry a read or a write out of scope unnoticed.

### Read scope

`read`, `ls`, `grep`, `find` and `data` are held to the workspace by [read-scope.ts](../../src/domains/safety/read-scope.ts) for workers and the other deterministic callers. A target is judged on every spelling the tool can open: the path as given, the physical path after links, and the fallbacks the read tools try when the path does not exist. A path that resolves outside the workspace asks at `default`, and a path that cannot be resolved counts as outside. Zero-access entries apply in every case. The operator's own session reads any path no zero-access entry covers at `default`, and at `yolo` reads anywhere except Clio's credential store and operator-authored zero-access entries.

Some trees outside the workspace are readable without an ask because Clio points the model at them: installed skills, plugins and extensions under the config directory, the user skill roots of interoperating agents, the offload scratch directory and the telemetry run scopes under the state directory, and the installed package's own `docs/`, `src/`, `README.md` and `CHANGELOG.md`. Roots the operator owns also admit a path that sits under the root as written, so a skill installed as a link into a dotfiles tree stays readable. A worker's sandbox read roots (the parent checkout and shared dependency trees of a task worktree) are exempt for that worker.

### Damage-control rules

Rules live in [damage-control-rules.yaml](../../damage-control-rules.yaml) and compile at load. A rule either blocks or asks, and a rule match is judged against each command a shell string would run, not only the string as a whole.

Hard blocks include `rm` of `/`, the home directory or everything in either, `sudo rm`, `rmdir --ignore-fail-on-non-empty`, `find -delete`, `rsync --delete`, `shred`, `chmod 777`, recursive `chmod` on system roots, recursive `chown` to root, `dd` to a device, `mkfs`, fork bombs, `kill -9 -1`, `killall -9`, `pkill -9`, clearing shell history, force pushes (`--force`, `-f` and `+` refspecs), `git reset --hard`, forced `git clean` without a preview flag, `git stash clear`, `git reflog expire`, `git gc --prune=now`, `git filter-branch`, `curl` or `wget` piped to a shell, writes to system roots through redirects or `tee`, cloud deletion commands (AWS, gcloud, Firebase, Vercel, Netlify, Wrangler), and SQL `DROP`, `TRUNCATE` and `DELETE` without a `WHERE`.

Confirmation rules ask: `git checkout -f`, `git checkout -- .`, `git restore .`, `git stash drop`, `git branch -d` or `-D`, deleting a remote branch with `git push`, `gcloud iam policies`, SQL `DELETE` by id, `truncate -s 0`, and `:>`. The whole-worktree spellings `./`, `:/` and a pathspec after `--` count as `.` for the two git rules. How the operator's own session treats each rule is in [Damage control at default](#damage-control-at-default); at `yolo` only the floor's rules hold.

Damage-control scans cover commands. A `write`, `edit`, `artifact`, `dispatch` or `tasks` call is scanned for its destination path alone, and a read-class call's payload is not scanned, so a file that documents `rm -rf /` can be written and a script that contains it is judged when it runs.

A project `.clio-coder/safety.yaml` can add path entries, but the built-in zero-access, read-only, no-write and no-delete defaults hold unless the project sets `disableDefaultPathPolicy: true`. The no-write defaults cover other agents' configuration directories, and the no-delete defaults cover `README*`, `LICENSE*`, `CLAUDE.md` and `~/.claude/`.

#### Delete targets

A shell delete is judged by where it lands, never by its flags. `rm -rf build` inside the workspace is an ordinary command. A delete is a hard block for the deterministic callers, under rule `delete-outside-workspace`, when it targets the workspace root, a path outside the workspace, the workspace's `.git`, or a path the shell names only at run time such as `$VAR` or a command substitution. Scratch roots (`/tmp`, `/var/tmp`, the system temp directory) are exempt, except for a checkout's own root and `.git`. The operator's own session at `default` adds `safety.scratchRoots` to the scratch roots and turns the block into an ask the safety judge decides; at `yolo` only the floor's `yolo-floor-delete-target` refuses a delete. The rule recognizes `rm`, `rmdir`, `unlink` and `find` (`-exec rm`, `-delete`) however they are quoted or wrapped: dequoted arguments, `command`, `env` and `sudo` prefixes, `timeout`, `xargs` and `find -exec` wrappers, `sh -c` and command substitutions. The same delete through an interpreter (`python -c` with `shutil.rmtree`), `eval`, a command name held in a variable, or another program such as `tar --remove-files` is not recognized, so it follows the ordinary command rails: it runs contained at `default`, goes to the judge when uncontained, runs at `yolo`, and asks for a worker. Globs and brace expansions are judged by the directory before the first wildcard.

Every rule is matched against each command a shell string would run, so an operator cannot hide one: `git restore . && echo ok`, `git restore .; ls`, `sh -c "git restore ."` and `$(git restore .)` all match. Command substitutions using `$(...)` or backticks are scanned inside double quotes too ([protected-artifacts.ts](../../src/domains/safety/protected-artifacts.ts)).

#### Matching details

The policy exempts rule matches only when every span is inside an inert quoted argument to `echo`, `printf`, `git commit` or `git tag` messages, or `grep` and `rg` patterns. Whole-command and segment scans remain active. SQL and operator matches, substitutions, pipelines, heredocs and executable wrapper words prevent the exemption. Each scan candidate must independently prove its matches inert before an exemption applies, so quoted prose cannot suppress a destructive normalized git command elsewhere in the same call. These checks inspect the shell command alone. A bash call's `cwd` is path metadata and cannot turn quoted documentation into shell execution.

Git damage-control scans also dequote simple-command words, join backslash-newline continuations, look through wrappers such as `env`, `sudo`, `nice` and `timeout` and through path-spelled `git`, and skip recognized git global options to find the subcommand. Original scans remain active, so normalization adds coverage without removing conservative matches. Combined short flags are expanded for `git clean`, `push` and `checkout`, and unique destructive long-option prefixes are expanded for `clean`, `checkout`, `reset` and `push`. Ambiguous prefixes and `--force-with-lease` are preserved.

- `git clean` previews with `-n` or `--dry-run` pass the safety net, including combined short flags and previews that also carry force flags, and then follow the ordinary command rails. Forced deletion without a preview flag stays blocked for the deterministic callers.
- `git push --force-with-lease`, including an explicit lease value, passes the safety net and then follows the outward-action row of the rules table. Unconditional `--force`, `-f` and plus-prefixed refspecs such as `git push origin +main` stay blocked for the deterministic callers and go to the judge in the operator's session at `default`.
- Whole-worktree `git checkout .` and forced checkout ask for the deterministic callers; the operator's session at `default` runs them after a snapshot.
- Restoring a named file from an explicit `--source` is an ordinary single-path restore. Whole-worktree restores, including `--staged .`, and branch deletion with `-d` or `-D` ask because they change repository state across the selected scope.

## Project policy

A project `.clio-coder/safety.yaml` (found by walking up from the working directory, schema `version: 1`) can declare:

| Key | Purpose |
| --- | --- |
| `commands` and `tasks` | Commands that run without an ask, each with `id`, `command`, optional `cwd`, `timeoutMs`, `maxOutputBytes`, `actionClass`, `shellOperators` (`deny` or `allow`), `env` (`mode: none` or `allowlist`), `requireConfirmation`, `rationale`, `owner` and `comment`. |
| `zeroAccessPaths`, `readOnlyPaths`, `noWritePaths`, `noDeletePaths` | Extra path entries, relative to the policy root. These are the operator rules that hold at `yolo`. |
| `disableDefaultPathPolicy` | Drops the built-in path defaults. |
| `informationFlow` | Source rules, recipient groups and pinned targets. See [information flow](../guide/information-flow.md). |

Unknown keys make the policy invalid. A policy takes effect only after the operator approves its exact bytes; see [Project trust](#project-trust). An unapproved policy grants nothing and its parse errors never block execution, but its `informationFlow` sources keep labeling what they name.

## Project trust

Five project surfaces carry privilege and are ignored until the operator approves their captured contents for this workspace. Safety, settings and hooks use byte digests; package surfaces use approved identity sets when every record pins its content ([workspace-trust.ts](../../src/core/workspace-trust.ts)):

| Surface | Files |
| --- | --- |
| `safety` | The nearest `.clio-coder/safety.yaml`. |
| `settings` | `.clio-coder/settings.yaml` and `.clio-coder/settings.local.yaml`. |
| `hooks` | `.clio-coder/hooks.yaml` and `.clio-coder/hooks.local.yaml`. |
| `extensions` | `.clio-coder/extensions/state.json`, the install state of the project's extensions. |
| `plugins` | `.clio-coder/plugins/state.json`, the install state of the project's library packages. |

```bash
clio-coder config trust safety|hooks|settings|extensions|plugins  # print captured files and the SHA-256 digest (read-only)
clio-coder config trust <surface> --hash <reviewed-sha256>        # approve the reviewed bytes or package identities
clio-coder config trust <surface> --revoke                        # remove the approval
```

Approval is per canonical workspace and stored under `<state>/workspace-trust/`. For `safety`, `settings` and `hooks`, approval pins captured bytes; the safety digest also binds the resolved source path, so an ancestor policy still needs approval for each workspace using it. An edited byte-approved surface reads `changed`. For `extensions` and `plugins`, review captures install-state bytes but approval records the package identities described below. Legacy unpinned package records retain byte-digest approval. The command exits 2 on a usage error and 1 when the files changed since review or none is readable. Approval takes effect on restart for `safety` and `settings`; hooks register on `/extensions reload`; `extensions` applies on `/extensions reload` and `plugins` on `/library reload`. Tool calls that invoke trust commands are blocked under `trust-authority` at every level. See [Commands and modes](../guide/commands-and-modes.md) for the command reference.

An ignored surface is not silent:

- A TUI session shows a `[clio-coder:trust]` notice for each present, unapproved `safety`, `settings`, `extensions` or `plugins` file at start, naming the file (the `state.json` for the last two), its verdict (`untrusted` or `changed`) and `clio-coder config trust <surface>`. The line reads `<file> is <verdict>; project <surface> ignored. Review with clio-coder config trust <surface>.` The notice is held for the transcript and stays until read. A headless run prints the same line to stderr. Hook files report their own issue when loaded.
- An ACP client receives the same facts in `_meta["clio-coder/trust"].ignored` on `session/new`, `session/load` and `session/resume`, one entry per ignored file with `surface`, `file`, `verdict` and `fix`, covering all five surfaces including `hooks` ([trust-notice.ts](../../src/engine/acp/trust-notice.ts)).

Trust is not the only filter on a trusted project settings layer. A project layer cannot carry credentials, cannot set `trustedUnmediated` on a target or external agent, cannot loosen `safety.autonomy`, and cannot set `safety.scratchRoots`, `safety.sandboxPassEnv`, `safety.sandboxUnixSockets`, `safety.unattendedAfterSeconds`, `safety.yoloAccepted` or `safety.judge`; each ignored key is reported as a layer issue.

### Project packages

Project extensions and library packages install from the repository's own state files, so their digest checks prove integrity and not consent. The `extensions` and `plugins` surfaces supply the consent.

- **What an unapproved workspace loads.** Each listing of the project's packages checks the surface. While it reads `untrusted` or `changed`, every project copy is blocked: it contributes no tools, hooks, runtime, skills, prompts, agents or playbooks, a blocked library package does not satisfy a dependency, and it neither shadows nor suppresses a user copy of the same ID, so the user copy keeps loading. User-scope packages never depend on workspace trust. A blocked copy stays listed. An enabled, valid, compatible one is marked `untrusted` in `extensions list`, or `requires trust` or `invalid` in the library views, and carries a warning that names `clio-coder config trust <surface>`.
- **What approval covers.** Package approval binds id, content digest, envelope digest, source, origin, trust flag and, for plugins, kind. Install time and the disabled list stay outside the identity. Reinstalling identical content, disabling or removing a package preserves consent. Enabling an unapproved identity or changing a recorded identity needs approval; legacy unpinned records still require exact state bytes. A running session rechecks approval before admitting resources.
- **Operator installs.** An operator project install can approve the identities of the records it wrote when the prior state was absent or trusted. Each record must still carry the digest the install wrote; a concurrent replacement stays unapproved. [workspace-trust.ts](../../src/core/workspace-trust.ts) captures the prior approval and rechecks it under the trust-record lock, so a concurrent revoke is not undone.
- **Imports.** Archive imports (`share import`, `/archive import`), `library import`, `interop adopt` and skill install offers never approve new identities. Existing approval remains usable when the resulting enabled identity set is still covered.
- **Task worktrees.** A task worktree that Clio Coder created can inherit the origin's `extensions` and `plugins` approval when its enabled identities are covered by that approval, or its state file is byte-identical to the approved origin. The origin's approval must remain current. Inheritance is evaluated at capture and writes no record of its own. The ownership claim at `<origin>/.clio-coder/worktrees/<runId>.task-owner.json` must identify the worktree ([task-worktree-claim.ts](../../src/core/task-worktree-claim.ts)); a hand-made worktree does not inherit approval.
- **Authority.** A model cannot approve a surface. Tool calls that invoke `config trust` are blocked under `trust-authority`, and model writes to the `<state>/workspace-trust/` records are refused at every level. Model writes to the installed resource trees, which hold the install-state files, are refused below `yolo`; at `yolo` the floor still refuses them under Clio's own config directory, and the project's `.clio-coder/` trees are not protected.

## Extensions and plugins

A plugin is content: skills, agents, prompt templates and playbooks, with Clio's own content under the Clio namespace of an Agent Plugin `plugin.json`. The stdio servers in a loadable plugin's root `mcp.json` become plugin-scope MCP declarations. They are never trusted automatically: each needs `clio-coder mcp trust <id>` exactly as a project server does, and the trust record binds the declaration and the plugin's recorded content digest. A foreign package, which `interop adopt` or `library import` installed, declares servers only while `integrations.projectResources.trustProjectImports` is true, and turning that setting off stops its running servers before their next call. An in-place edit of the installed tree is drift: the plugin stops loading, its declarations disappear, and a server already running stops before its next call, as it does when the plugin is disabled or removed. An update or reinstall records a new content digest, so the server stays declared and its trust goes stale. A session that resolved the declaration before the update refuses every launch and call of that server until it restarts, even after the server is trusted again, because the session's declaration still binds the old digest. Clio does not execute plugin hooks. Installing, enabling or browsing a plugin never runs code inside Clio.

An extension is Clio code in its own process, declared in `clio-coder-extension.yaml`. At runtime api 2 it can register hooks, runtime tools named `extension_<id>__<tool>`, commands named `/ext:<id>:<name>`, workspaces and skins, and interviews. Discovery and review read only the manifest. An extension and a plugin are separate packages with their own digest, state and consent. An extension may name the one plugin it serves with `plugin: <name>`. That link alone lets a command declare `replaces: prompt` to answer a prompt of that plugin, and the takeover applies only while the plugin is installed and enabled.

**Capability envelope.** The operator consents to what an extension may do, not to its bytes. The envelope covers its commands, events and timer, hooks with their failure modes, runtime tools with their action class, interface slots, workspaces with their regions and keys, watched paths, the content it may read (`prompt`, `tool-args`, `tool-results`, `assistant-text`), file read and write roots, whether it may run programs or use the network, the host `state` it keeps (per session, across sessions) and `takesOver`, the plugin prompts its commands answer. One envelope renderer feeds every review. `clio-coder extensions install` prints it before the write, the Library review and the `share import` plan show it, and an update review names what reaches further than the installed copy (`Reaches further than the installed copy:`) or says it reaches no further.

**Digest binding.** The review hashes its envelope, and the install applies only that digest. A package whose envelope changed after review is refused with `extension capability envelope differs from the one reviewed; review a fresh plan`. The install records the envelope digest beside the content digest. At load, the recorded envelope digest must match the manifest's envelope, and a mismatch leaves the package invalid and unloaded until it is reinstalled and reviewed. A record with no envelope digest fails the same way.

**Confinement.** The runtime child runs in a private copy of the package under Node permission flags built from the manifest. Those flags are a seat belt against mistakes and not a boundary against hostile code. When an OS sandbox exists (bubblewrap on Linux, or `sandbox-exec` on macOS, which is unverified on a real macOS build), the child also runs inside it with the filesystem read-only outside its declared write roots, secrets masked, Clio-managed paths (`.clio-coder`, the config directory, workspace trust) and Git metadata read-only, and an empty network namespace unless the manifest declares `net: true`; the Unix-socket filter applies there too. A declared write root may not name the workspace root or `.clio-coder`. Without a sandbox backend the Node flags apply alone and a declared `net: false` is not enforced. The launch always requests the sandbox in `auto` mode, so `safety.sandbox` does not change it. `/extensions` shows a `Confinement:` line per runtime, for example `bwrap OS sandbox; network blocked (enforced); secrets masked and Clio-managed paths read-only`, or `no OS sandbox (bubblewrap (bwrap) is not installed); Node flags only, so the declared network ban is not enforced`.

**Package code.** Two authoring commands execute package code on request. `clio-coder extensions validate <path>` runs the package's startup code in a private copy under its declared Node permissions and inside the OS sandbox when one is available, without invoking a handler, and prints that notice with the result. `clio-coder extensions test <path>` runs the package's own `*.test.ts` files under Node's test runner in the package directory. At `default`, a model shell call that runs either one, or a `clio-coder share import` that is not a dry run, is held for the operator's approval the way `library install` is, because the model may have written the package or the archive. Run them only on code you trust. A share archive's extension entries install through the same envelope review and digest check. Project-scope extensions also need the workspace approval in [project trust](#project-trust).

## Information flow

Information flow keeps named content away from destinations the operator did not choose. Source rules in the project policy label content when a read, shell command or `@file` reference touches a source, and every model request, mediated outbound tool call and System One engine request is checked against the labels the session carries. A model-request refusal holds at `yolo`. Under `yolo` (the operator's session, or a worker that inherited it) a mediated outbound tool call such as `web_fetch` or an MCP tool, and a source read while the policy is unavailable, are not refused; the source's label is still absorbed, so the session keeps the record and a later model request to a disallowed target is still refused. Claude Code, Codex, ACP agents and pane peers cannot admit their own model requests, so they are refused at launch when any source rule does not admit their target. The contract, limits and recovery steps are in [information flow](../guide/information-flow.md). Implementation: [information-flow.ts](../../src/domains/safety/information-flow.ts) and [flow-ledger.ts](../../src/entry/flow-ledger.ts).

## Approvals

A parked call carries a request id. A main-agent approval resumes only that call. A worker escalation approval also resumes only the parked call. A denial is remembered for a matching tool, arguments, approval axis, and safety classification within that worker run, so an identical call is denied without a new card. An approval is never remembered. The approval card explains a decision already made; it never changes the decision. At `default` the safety judge sees every main-session ask that is not operator-only before anyone is asked. Who answers what remains depends on the surface:

- The TUI: the operator, in the approval card, which resolves as denied after the [unattended timeout](#unattended-resolution).
- An ACP client, the GUI included: the client's own permission request, answered by its operator. A client that advertises `clio-coder/interviews` or `clio-coder/workerPermissions` at initialize is attended, which also routes `ask_user`, harness cards and forwarded worker asks to that operator. A client that advertises neither keeps the unattended behavior. See [ACP architecture](acp.md).
- A headless `clio-coder run`: nobody is attached, so the ask is denied; see [Headless runs](#headless-runs).
- A dispatched worker: the permit's ask route, which `fleet.permissions.mode` sets by default. See [Worker permits](#worker-permits).
- An ACP delegation peer: the mediator denies the ask without stalling.

`WorkerSpec.onPermission` (`deny`, `fail` or `escalate`) is the wire form of a worker's ask route ([spec-contract.ts](../../src/worker/spec-contract.ts)). A permit that routes asks to `main` travels as `escalate` with a main-authority binding.

| `fleet.permissions.mode` | A worker's ask |
| --- | --- |
| `judge` (default) | An ordinary ask on a native local worker goes to the main session's safety judge in the orchestrator while the main session runs at `default`; an allow grants the call once and anything else denies it. Operator-authority asks go to an attended operator and are denied headless. Runs as `deny` wherever no judge can answer; see [Workers at each level](#workers-at-each-level). |
| `deny` | Becomes a structured tool denial and the run continues. A refused execute call counts toward a per-run limit; the limit, exit code and denial format are in [worker dispatch mechanics](worker-dispatch-mechanics.md). |
| `fail` | Ends the run at the first ask as `permission_required` (exit 3). |
| `escalate` | Parks the call and forwards it to the operator. `fleet.permissions.escalation.timeoutMs` (default `120000`) bounds the wait and `fleet.permissions.escalation.fallback` (`deny` default, or `fail`) applies on timeout. With nobody attached (a headless run, an ACP client without `clio-coder/workerPermissions`, the fleet CLI) the fallback applies at once. |
| `main` | Routes an ordinary ask to the main agent instead of the operator. |

Under `main`, the main agent grants an ask only at `yolo`, only when the effect sits inside the operator's delegation ceiling for the turn and the worker's permit, and only when the same call would be admitted as the main agent's own at `yolo` without the operator's own scope, so damage-control rules and path policy still hold for a grant ([grant-authority.ts](../../src/domains/dispatch/grant-authority.ts)). Such a grant still asks for `outside-file-replacement`, except for a file the session created and nothing else has written since; that exception tracks files by identity (device, inode, size and modification time) in memory, per session, and the record is cleared when the session is parked. Below `yolo` an attended operator decides, and a headless run denies at once. A rail only a person may clear, a hard block, a gateway-wrapped call and a call too large to evaluate are never main-grantable. The worker re-admits a granted call under its unchanged permit before it runs. Under `main` and `judge`, a host denial of a main-authority execute ask counts toward the worker's refusal limit.

Runtime support is checked at dispatch. Subprocess runtimes admit only `deny`. The Claude SDK admits `deny` and `fail` but cannot park an `escalate` request. Only native local workers take `main` grants and judge verdicts. A dispatch under `main` to any other runtime, or to a remote placement, is refused with an error that names `escalate` and `deny` as alternatives, while `judge` there runs as `deny`. Runs started outside the dispatch tool, such as a slash command or the watchdog, have no main agent waiting, so their `main` asks narrow to `deny`.

### Approval cards

The card's keys are `Enter` to allow once, `Alt+X` to stop the turn, `Esc` or `Ctrl+C` to deny, `Alt+V` to inspect a parked `write` or `edit`, `Alt+T` to fold the standing approval terms and the arrow keys to scroll a tall card. Letters typed while the card is open go to the composer. A card that another screen closes without an answer is presented again. While the composer holds a draft, `Enter` is inert and the entry becomes `Backspace` to clear the draft, so the habitual send key cannot allow a call. A card the safety judge handed over says why: no verdict, or repeated blocks. While `safety.unattendedAfterSeconds` is above 0, a main-agent card shows its countdown; any key stops it.

A bash approval card also carries an `Effect:` row, one plain sentence per step of the command, such as "Deletes build recursively". The host writes the sentences from the full command and checks existing paths on disk, redacts secrets and bounds each sentence at 240 characters. The card shows three sentences and folds the rest into `and N more`, except that severe sentences (deletes, stops, history rewrites) stay visible up to eight. A worker's ask carries the sentences its worker wrote, and an ACP permission request carries them as `consequenceLines`. They are presentation only. Admission never reads them, so a command Clio Coder does not recognize shows no row and a recognized one is not blocked or asked about because of it. The safety judge reads the same sentences as features. The reader works on the literal command, so an operand written as `$DIR` is shown as `$DIR`. Bidirectional control characters in card text are escaped as `\u{...}`.

A shell word written with ANSI-C quoting (`$'...'`) is decoded before admission, so path and write rules judge what the shell will see. An ambiguous ANSI-C escape or a locale-quoted `$"..."` word cannot be inspected, so an uncontained call carrying one asks under rule `bash-hidden-quoting`.

### Running long jobs unattended

Three setups keep a long job moving with nobody at the terminal:

- **Attended `default` with the unattended timeout.** The session contains its shell work, snapshots before destructive steps, and the judge answers most asks. A tool that needs a local Unix socket or a credential variable fails contained; the model reruns it with `unsandboxed: true` for the judge, or list a variable it must keep in `safety.sandboxPassEnv`. A card or question nobody answers resolves after `safety.unattendedAfterSeconds`, and the turn continues. What Clio decided while the operator was away shows on the decision board and in the exit summary's `Unattended` line.
- **Headless `clio-coder run` at `default`.** The same containment, snapshots and judge apply, and every ask the judge does not allow is denied at once. Put decisions in the task prompt, because the judge reads the operator's messages and nothing else.
- **`--autonomy yolo` in a container.** Nothing asks and only the floor, operator rules and ceilings block. Run it in a container or another disposable environment, because commands run unsandboxed with the operator's credentials.

```bash
clio-coder run --autonomy yolo "Inspect the locking code and report possible faults or hangs."
```

When an ordinary call unexpectedly asks or is refused, report the Clio Coder version, effective session autonomy, exact tool arguments including `cwd`, and whether the call came from the main agent or a worker. Include the rule or reason code and, when one is present, the `safety.judged` record. These distinguish a floor block, a judge verdict, a worker's ask route and a main-agent admission defect.

## Worker permits

The host resolves one immutable permit per worker attempt ([worker-permit.ts](../../src/domains/safety/worker-permit.ts)) and the run's `run.settled` record carries its digest as the labelled hash `safety.permit.digest`. It separates a hard ceiling from a standing allowance inside it, and nothing a worker, a recipe or a task requests can widen either. An ACP delegation peer runs its own tool loop, so its permit is a record-only ceiling that Clio does not enforce: Clio answers only the permission requests the peer sends under the agent's `toolGovernance`.

- **Ceiling.** The capability class, the admitted tools that the turn's delegation ceiling also covers, the read-only restriction, the write roots, and what the runtime itself enforces. A class bounds its tools: `read-only` admits only read tools, `artifact-write` only the artifact write, `verification` no writes and no bash (checks run through typed verification). `orchestration` agents cannot run as workers, `internal` is available only to host-selected helper protocols, and orchestrator-only tools (`dispatch`, `ask_user`) are never admitted to a worker.
- **Allowance.** `git` is `inspect` (default) or `worktree`, which lets a `workspace-edit` worker stage and commit through typed Git inside its own task worktree and nowhere else. `asks` is `deny`, `fail` or `main`, and `fleet.permissions.mode` is its ceiling (`escalate` maps to `main` with operator authority; `judge` maps to `main` with main authority, decided by the safety judge). A recipe or task may narrow it; a recipe that declares `asks: main` under mode `deny` or `fail` resolves to the operator's configured route instead of escalating. A recipe's `permissions:` block (`git`, `asks`) declares the allowance for its workers, and `git: worktree` requires the `workspace-edit` class. Per-task narrowing can only narrow: widening `git` to `worktree` or `asks` to `main` for one task is an admission error, a retry never runs wider than the attempt it replaces, and a recipe routing asks to `main` never raises who decides them.
- **Operator yolo.** When the session autonomy is `yolo`, the runtime mediates every call, the run is not read-only, and neither the recipe nor the task declares `asks: deny` or `asks: fail`, the permit carries `executeAutonomy: yolo`; the field keeps its historical name. The worker is then admitted the true yolo way for every action class: only the floor, operator rules and its dispatch ceilings refuse a call, and its Git allowance and ask route are not consulted. A retry inherits the grant only when the attempt it replaces had it. At `default` session autonomy workers hold no such grant.
- **Unmediated runtimes.** A runtime that runs its own tool loop (Claude Code, Codex, other CLIs) is refused write-capable work unless the operator sets `trustedUnmediated: true` on the target in user settings. The opt-in is part of the worker's permit.

## Worker OS sandbox

`safety.sandbox` runs the commands of a dispatched native (HTTP runtime) worker under an OS sandbox: the `bash` tool, `run_script` and verification checks. Subprocess and SDK runtimes and workers placed on a `fleet.nodes` node are not sandboxed. The main session's commands use the [main-session sandbox](#the-main-session-sandbox) at `default` instead. Native `write` and `edit` run outside the child sandbox but honor the same read-only paths.

| Value | Behavior |
| --- | --- |
| `auto` (default) | Sandboxes when a backend is available. Otherwise worker commands run unsandboxed and a worker-diagnostics line `[worker] sandbox unavailable (...)` is written once, and the main session's commands at `default` run uncontained. |
| `required` | Refuses worker commands when no backend is available. The main session's commands at `default` run uncontained with the default rails, and `yolo` runs its scripts in the main-session sandbox or refuses them without a backend. |
| `off` | Never sandboxes, for workers or the main session. |

Backends ([availability.ts](../../src/core/sandbox/availability.ts)): Linux uses bubblewrap (`/usr/bin/bwrap` or `bwrap` on `PATH`) and is probed with the same namespaces a real command uses, so a kernel or container that forbids unprivileged user namespaces reports unavailable. macOS uses a `sandbox-exec` seatbelt profile that is unverified on a real macOS build. Other platforms, Windows included, have no backend. The probe runs once per process.

Policy ([worker-policy.ts](../../src/core/sandbox/worker-policy.ts)): the filesystem is readable and writes land only in the worker's writable roots and temporary space, which is a private `/tmp` under bubblewrap and the shared `/private/tmp` and `/private/var/folders` under Seatbelt. Writable roots are the run's `write_roots`, else its task worktree, else its working directory, and a read-only run has none. `.git` and `.clio-coder` inside a writable root stay read-only except for the Git metadata that typed Git task mutations need. Every hooks directory git could run for the worker's tree, `core.hooksPath` included, stays read-only when it lies inside a writable root. Secret paths and runtime escape paths (the user runtime directory, the container sockets) are masked, secret files in the worker's worktree and checkouts are masked, credential variables are scrubbed from its environment (see [The main-session sandbox](#the-main-session-sandbox)), the Unix-socket filter applies, `SSH_AUTH_SOCK` is unset, and `TMPDIR` points at the private `/tmp` under bubblewrap. Network is off unless `safety.sandboxNetwork` is `true` or the run holds `web_fetch`. A worker starts each admitted MCP server's process under the same policy. The operator can give one server network without giving it to the worker's commands: `clio-coder mcp trust <id> --network` records the grant on a project or plugin server's trust record, and `network: true` grants it in a user-scope declaration. Re-trusting without `--network` drops the grant. A project or plugin declaration cannot grant itself network, so its own `network` field is ignored and `clio-coder mcp list` reports it as a warning; the listing shows each server's grant and its source. A granted server's process still sees the home read-only with credential directories masked, and other servers and the worker's commands keep the run's network policy. On Linux a granted server runs without `--unshare-net`, so it shares the host network namespace: the internet, services listening on localhost, and abstract Unix sockets. On macOS the grant adds `(allow network*)` and `(allow system-socket)` to the Seatbelt profile ([seatbelt.ts](../../src/core/sandbox/seatbelt.ts)), which has not been exercised on macOS. Credential masking is a denylist of known paths ([worker-process.ts](../../src/core/sandbox/worker-process.ts)), so any other secret readable in the home can leave through a granted server. A writing worker loses the grant for a server whose code it could change ([worker-mcp.ts](../../src/domains/dispatch/worker-mcp.ts)): when one of the run's write roots contains or lies inside the server's launch cwd, the directory of a file it runs, or for a project server the project root, the worker withholds that server's grant, and admission and the dispatch result name the server and the reason. For a project server the files it runs are its bound entry files; for a user or plugin server they are every existing file its command and arguments name. A withheld server starts under the run's network policy, and with `safety.sandbox` off it runs unconfined. A read-only worker keeps the grant. An edit to a module the server imports is not bound, so a writer's edit persists into a later read-only run that holds the grant. A missing exact-file write root cannot be created by a command, so the worker's safety line tells it to create the file with the `write` tool first.

## System One and the safety net

System One is an optional experimental decision model. Its sites record detached readings without delaying calls or results, and they are silent when no engine is bound, when the engine is slow or fails, and when the answering build has no fitted cut. At the safety sites a reading adds no confirmation, banner or delay.

- **The yolo gate.** At `yolo`, in an interactive session, an `execute` call that the classifier did not recognize starts a detached System One reading that is recorded for training. It never parks, denies or delays the call. A call the classifier already blocks or recognizes does not reach it, and headless runs and ACP sessions have no gate.
- **Tool-result screening.** Results of `web_fetch`, `web_read` and MCP tools start a detached reading for text that directs an AI agent. The deterministic marker scan still applies.
- **Card advisory.** An ordinary approval card can show one advisory sentence about the call's blast radius when a `toolCall` engine is bound. It says it is advisory, cannot delay the card and does not change what allow, deny or stop do.

The safety judge is not a System One site. It shares only the one-shot port and the reach ladder's wording. The settings, sites and records are in the [System One guide](../guide/system-one.md) and [System One architecture](system-one.md).

## Workers

- Every worker permit is derived from the host's settings. A worker inherits the main session's level only through its permit, as [Worker permits](#worker-permits) describes. A read-only dispatch adds the restriction above, and its permit's ceiling records `readOnly: true`, whether or not the worker ever tried to write.
- A task that declares `write_roots` is confined to them and cannot dispatch. Without an OS sandbox covering the run it also loses `bash`, `verify` and `run_script`, and a `write_roots_checks_withheld` scope notice says so. With the sandbox it keeps `bash`, `verify` and `run_script` inside the roots.
- A task with `worktree: true` runs in its own git worktree, by default at `.clio-coder/worktrees/<runId>/` (`fleet.worktrees.root` can move the working tree), on branch `clio-coder/task/<runId>`. See [Fleet dispatch](../guide/fleet-dispatch.md).
- A checkout writer lease lets one Clio Coder process at a time dispatch workspace-edit workers into a checkout. A second process is refused with `checkout_writer_lease_held` ([checkout-writer-lease.ts](../../src/domains/dispatch/checkout-writer-lease.ts)).
- Workers carry the approved information-flow source rules and the restrictions their inherited context holds, and judge every model request against them.

## Evidence and the finish contract

- The finish contract ([finish-contract.ts](../../src/domains/safety/finish-contract.ts)) checks the end of a turn that changed files, looking at the session entries since the last user message, at most 80. It looks for validation evidence, such as a validation command that ran or a dispatch run record (`dispatch_run_record`), or for a `limitation` receipt. With neither, the footer shows `change not verified; inspect the turn receipt` and the decision is journaled as `completion.evaluated`. At high rigor the contract instead withholds completion and re-prompts the model to validate or record a limitation, unless the task scope forbids recovery. The contract settles without that advisory when the turn made no mutation, left no net workspace change after an undo, changed only paths outside the workspace or Clio Coder configuration, or only deleted tests or docs (non-source paths) or a path the operator's message asked to delete. A blocked call and an out-of-workspace write are not unverified changes. A write to `.clio-coder/settings.yaml`, `.clio-coder/settings.local.yaml` or `.clio-coder/fleets/<name>.md` is Clio Coder configuration and does not count as a changed file. Validation evidence is retained behind workspace `cd` prefixes.
- When checks pass but behavior coverage is unknown, the footer shows an info line, `checks passed; coverage of the change not measured`, which clears at the next turn. With validation evidence but no passed check it reads `validation evidence recorded; coverage of the change not measured`. Both are operator status and never a request to run more checks.
- A [project quality policy](../guide/quality-policy.md) adds path-scoped required checks. Native verification receipts must match current source, check declaration, and policy snapshots. A valid policy selects high rigor unless explicitly overridden; recovery stays within the turn's existing authority. Check-scoped limitations settle requirements only when the policy explicitly allows them, and remain unverified. Rigor resolution and the validation contract are described in that guide.
- The citation-grounding assessor (`assessor.citation-grounding`, [citation-grounding.ts](../../src/domains/safety/citation-grounding.ts)) records which lines a numbered `read` or a grep match printed. When a final answer cites `path:line` into a file that was read without line numbers at a line no tool printed, it carries the turn onward once with the unbacked citations. It never blocks the answer, skips files the session mutated, and cannot see bash output or `code_nav` symbol lines.
- Checks named in a dispatch's `verification` run on the host after the worker finishes. The worker's report is a claim until then.
- A finished run's `run.settled` record sits in a hash-chained journal that `run.sealed` closes, and `clio-coder telemetry verify` recomputes the chain, so an edited record fails ([Telemetry](telemetry.md#verify)). The chain detects edits that leave it stale; it is not a signature, so a journal rewritten with every link recomputed still verifies.

## Decision reason codes

Each `tool.decided` record carries the decision's `reasonCode`. The autonomy redesign added these:

| Reason code | Meaning |
| --- | --- |
| `yolo-floor:<rule id>` | Blocked by the [yolo floor](#the-yolo-floor), at either level. |
| `operator-rule:<reason code>` | Blocked at `yolo` by an operator-authored rule in an approved `.clio-coder/safety.yaml`, such as `operator-rule:path-policy:noDeletePaths` or `operator-rule:secret_path_bash`. |
| `yolo-admitted:<reason code>` | Admitted at `yolo` past a rail that would have asked or blocked, such as `yolo-admitted:damage-control:git-reset-hard`. |
| `snapshot-recoverable` | Admitted at `default` because the workspace snapshot taken right before the call undoes it. |
| `delete-without-snapshot` | Asked at `default` because a workspace delete has no snapshot to undo it: no Git work tree, or `safety.snapshots: off`. |
| `snapshot-required` | Refused because a call admitted on the strength of a snapshot could not get one, or a ref it destroys or moves could not be pinned. |
| `git-hooks-changed` | Asked of the operator only, at `default`, because a git command would run hook files or executable git config added or changed since the session's baseline. |
| `git-control-file` | Asked at `default` because a typed write, edit or artifact call targets one of the repository's git hooks, config, `commondir` or `.git` pointer files: an operator ask for the main session, a main-authority ask for a worker. |
| `contained:system-modify-confirm` | A contained system change admitted at `default` without the ask it would carry uncontained. Other contained calls keep the reason code of the rail that passed them and carry the sandbox on the decision. |
| `safety-judge:allow` | Admitted by the safety judge. |
| `safety-judge:<rule>` | Refused by the safety judge under that rule category. |

The safety judge also journals its own `safety.judged` records, and an unattended card resolution is an `approval.resolved` record with `decidedBy: unattended`.

## Platform limits

- **Windows** has no sandbox backend, so nothing is contained there and `default` keeps the uncontained rails: recognized commands run and the judge reviews the rest. The `bash` tool resolves Git Bash, the first `bash.exe` on `PATH` and then the standard Git for Windows locations, and never the WSL launcher under the system directory or `WindowsApps` ([bash-shell.ts](../../src/core/bash-shell.ts)). With no usable bash the tool is not offered, `find` and `ls` stay attached, and dispatch admission drops `bash` so worker tool signatures still match. Yolo is never refused as root there.
- **macOS** uses a Seatbelt profile that has not been verified on a real macOS build.
- **Linux** needs bubblewrap and unprivileged user namespaces; a container that forbids them reports the backend unavailable.
- **What the sandbox does not hide.** The environment scrub and the secret-file masks match names and value shapes, so a credential under an unrecognized name, a secret file with an unlisted name, one inside a skipped dependency or build tree, an unmodified tracked secret, and anything past the 512-mask limit stay readable. Credential masking in the home directory is a denylist of known paths. The path policy still refuses a command that names a zero-access path, but not a program that opens one by itself.
- **Unix sockets.** The seccomp filter needs bubblewrap to load it; without it the fallback masks leave abstract-namespace sockets and sockets created after the launch reachable, and `clio-coder doctor` warns. The Seatbelt socket rules have not been run on macOS. With the filter on, tools that need a local socket fail inside the sandbox and need an unsandboxed rerun.
- **Network stays on** for contained commands, so a contained command can send anything it can read to a host it can reach. Outward detection names known executables; an outward step it does not name runs contained, without the credentials the sandbox hides.
- **The floor reads text.** An interpreter that deletes through its own API, or a path built at run time, is not seen at either level.
- **Clio's own git.** It is hardened by fixed options and, after drift at `default`, by per-key overrides; a changed key git cannot override from the command line still applies to Clio's hook-running operations, and git on remote fleet nodes gets no such hardening.
