## Defects

### D1 — `evidence inspect` prints an autonomy value the canonical projection withheld (#233)

`renderEvidence` (`src/cli/evidence.ts:204-209`) prints the canonical trust projection and then unconditionally appends the legacy provenance transcript, gated only on the receipt carrying the field. It never consults `trustStatus`.

On a v20 receipt one axis renders three times in two vocabularies:

```
trust 2ti5s6hekkkj: … mediated; context recorded; completion not applicable
  trust_status=v1 … autonomyEnforcement:enforced …
provenance 2ti5s6hekkkj:
  autonomy enforcement: mediated autonomy=full-auto
```

On a receipt whose seal fails it is worse. Building a bundle from a v19 receipt with the 0.3.8 binary, so the artifact is fresh rather than stale:

```
$ clio-coder evidence build --run 3snom8j463se
error: run 3snom8j463se: receipt integrity: integrity invalid
$ clio-coder evidence inspect run-3snom8j463se
trust 3snom8j463se: seal broken; … autonomy not recorded; context not recorded; completion not recorded
  trust_status=v1 artifactIntegrity:failed … autonomyEnforcement:absent …
provenance 3snom8j463se:
  autonomy enforcement: mediated autonomy=read-only
```

The projection correctly fails closed and reports every axis `absent`; the block two lines below reads the same unverified receipt and prints a concrete value as fact. Dispatch has the same shape with a third renderer, `enforcement=mediated:auto-edit`, which `monitor` omits.

This is the symptom #162 named in its own problem statement.

### D2 — starting a second clio-coder process marks every live fleet failed (#235)

`assignments.json` is machine-wide. The dispatch extension's startup reconciliation sweeps every record still marked `running` and, for one that has claimed a verdict owner, settles it `failed` with no check that the owning process is alive (`assignment-reconcile.ts:59-63`, called from `extension.ts:6071-6090` selecting on `record.status === "running"` alone).

Deterministic reproduction, no model call. Two code-only v5 contracts, `reconcile` (a `sleep 180` step then a no-op) and `tiny` (one no-op):

```
# process 1
$ clio-coder fleet run reconcile &
$ sleep 15
BEFORE: {"assignmentId":"fleet-60d52ad48cc8","attempts":[],"terminalRunId":null,
         "status":"running","verdictOwner":"fleet"}

# process 2, unrelated, while process 1 is 15s into a 180s step
$ clio-coder fleet run tiny
fleet tiny: 1/1 steps succeeded

AFTER : {"assignmentId":"fleet-60d52ad48cc8","attempts":["fleet-60d52ad48cc8"],
         "terminalRunId":"fleet-60d52ad48cc8","status":"failed","verdictOwner":"fleet"}
```

Process 1 went on to run its step to completion (`step hold code:slow: passed exit=0 180016ms`). The sweep announces itself as `[dispatch] assignment reconcile: recovered=0 abandoned=1`.

First observed in a real four-step fleet, `fleet-9c6d0b63d464`, where at `01:21:57Z` the row read `failed` with `terminalRunId: "376l7b2ru89e"` while the ledger had `endedAt: null`, both settled steps `succeeded: true`, and the third agent running until an operator abort at `01:23:20Z`. The row was simultaneously premature, wrong, and mis-attributed to a green run.

The file header states the assumption plainly: "every durable record still marked `running` after a crash is orphaned." True per-process, false for a store shared across processes. The `stop()` handler thirty lines below already reasons about sibling Clio processes; this pass does not.

`#225` closed the case where the row lied optimistically. It now lies pessimistically, in a shape that needs no fleet of its own to trigger.

## What the 0.3.7 report got wrong

Its verdict called the empty vote tally "the specified deterministic behaviour": *"`tally` renders empty because the vote legitimately found `no_verdict_field`: neither member emitted a parseable `verdict` field."* That reading is why #230 existed and was only found later. Nothing had ever asked a member for a verdict, and every unnamed council's vote resolved to `no_verdict_field` on every input. This round confirms the fix with a real tally (`{"yes": 2}`) over ballots members were actually asked to cast, and treats an empty tally as a failure until proven otherwise.

## Release verdict

**Not ready as it stands. One blocker: #235.** Everything else in the release verifies, and most of it verifies well.

#235 is a regression introduced by this release's own #225 fix. Any second `clio-coder` process on the machine settles every live fleet's durable assignment row to `failed`, while the fleet keeps running. It needs no fleet of its own to trigger, reproduces in under thirty seconds with no model call, and corrupts the record that `monitor`, `wait`, and any automation read. A TUI session beside a CLI command is the ordinary way this tool is used; this whole test session was that shape. It should not ship. The fix is bounded: reconciliation needs a liveness check against durable owner evidence, in the shape `state/checkout-writer-leases/` already uses, rather than treating `status === "running"` as proof of a crash.

The substance of the release is otherwise sound and is verified against sealed evidence rather than screen output.

The headline fix works on both halves. A concurrent operator edit made during a live fleet survives with a closed write record and is reported `unattributed` with `attributionComplete: true`, and the same edit is rolled back by a run that made a successful `bash` call, with `attributionComplete: false` — proved by git object hashes on tracked files, not by what the screen said. Enforcement is intact: a step that genuinely wrote outside its boundary still failed, was attributed to the step that wrote, and was restored to exact baseline bytes. That is the bug that destroyed three of the operator's real edits, and it is closed.

A declared write path that git ignores is refused at `fleet validate`, at `fleet run` preflight, and in the `/fleet run` preview, with a diagnostic that names the path, cites `.gitignore:1:work/`, explains why an ignored boundary can only certify an unobserved window, and gives both remedies. The real portus contract stops validating as a result, which is correct, and reads clearly enough to act on.

`/council` works in both synthesis modes for the first time. Vote members are asked for a ballot, seal a `council-ballot` postcondition, and produce a real majority tally; judge admission no longer dies before its first member and the judge answers the coordinator rather than its recipe; `/share` renders a bounded block with labelled member answers and the synthesis line for both. `configure` refuses a model the target does not serve while naming what it does serve, `--force` still saves, `doctor` reports it, and `degraded` fires correctly on the operator's own two misconfigured targets. Typed scope is authoritative: a dispatch declaring no intent is now silent where it used to warn on nearly every dispatch, a declaration produces exactly one bounded notice naming the omitted paths, the approval preview renders inferred scope in full instead of a bare hash, and a declaration closes a scope inference would have widened. All five Settings Center number editors refuse out-of-bounds values by name, keep the editor open, and write nothing on a session-only apply.

Four defects are worth fixing but do not hold the release: #234 and #236 are presentation gaps where the correct information exists elsewhere, #237 is incomplete cross-surface parity on a feature that is a clear improvement over 0.3.7 even where it falls short, and #238 makes an intended version retirement read as corruption, which is confusing rather than dangerous. #239 is a two-line fix that should ride along with #235 since both are in dispatch.

Two things were not run and should not be read as passes: the delegation-plan splice path of the ignored-write refusal, and a council member that seals no conforming ballot.
