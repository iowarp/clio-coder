After the baseline was taken, the operator raised the router's `--sleep-idle-seconds` from 60 to 300 in the systemd unit (2026-08-29, backup `llama-server.service.bak-20260829-pre-sleep300`), because brief 05's pre-warm is wasted when the model sleeps before the user's first turn. The change affects only idle behavior, not prefill or generation throughput; the after-run's resume step still waits until the router reports the model `sleeping` before waking it, so both runs resume from the same cold state. The sleep flag matters for the measurement: a model idle for a minute sleeps, and the router answers the first request during the wake with a non-JSON `proxy error`, which Clio's engine records as an assistant entry with `stopReason: error` and `errorMessage: "Connection error."` at `apiMs: 2` before retrying. Each measurement below is taken with the model awake, confirmed by a throwaway request whose output is discarded, so no wake failure or load time lands in the numbers.

## Server tuning pass (before the baseline)

The operator authorized tuning mini's server, including a llama.cpp upgrade, before the baseline was taken. Everything below was measured on 2026-08-29 with `llama-bench` (`-ngl 99 -fa 1 -ctk q8_0 -ctv q8_0 -b 2048`, two repetitions) or with a chat-completions probe that reads the server's `timings`. The configuration above is the result and is frozen for both measurements.

Throughput levers, all within noise on this model and GPU (AMD Radeon AI PRO R9700, gfx1201, ROCm 7.2.0, 2725 MHz and 220 W at a 95 °C junction under prefill):

| Variant | pp4096 t/s | pp16384 t/s | tg t/s |
| --- | --- | --- | --- |
| running build `b10569-12-g2115b73d8`, ubatch 512 (as served) | 1216 | 979 | 29.7 |
| ubatch 1024 | 1235 | 1000 | 29.7 |
| ubatch 2048 | 1227 | 997 | 29.7 |
| KV f16 instead of q8_0, ubatch 1024 | 1249 | 1004 | 30.3 |
| flash attention off | 1016 | not run | 30.0 |
| `GGML_CUDA_FORCE_MMQ=1` | 1256 | 1002 | 29.6 |
| `GGML_CUDA_FORCE_CUBLAS=1` | 1241 | 1001 | 29.6 |
| upstream `b10687` (c841aee), same flags and the router's `--worker-bin` patch reapplied | 1185 ± 85 | 996 | 29.6 |

The upgrade to `b10687` was built (ROCm and Vulkan, under `~/src/llama.cpp-b10687` on mini) and not deployed: it moves nothing on this model, and the running build stays so the router and every worker keep one version. f16 KV would double KV memory at 262144 tokens for a 1 to 2 percent gain and is not taken. IQ4_NL is the only Qwen3.8 quantization on the host.

The lever that does move is not throughput. Qwen3.8 is a hybrid architecture with recurrent (gated-deltanet) layers, and llama.cpp cannot roll recurrent state back to an arbitrary token, so a divergence inside a cached prefix is re-prefilled from the last context checkpoint, not from the changed byte. Checkpoints are written at the end of each processed prompt and only when at least `--checkpoint-min-step` tokens separate them. Probe with a four-turn conversation of about 4096 tokens per turn, then one changed line inside an earlier turn:

| Request | default (32 checkpoints, min step 8192) | 64 checkpoints, min step 1024 |
| --- | --- | --- |
| grow turn 2, 3, 4 (pure append) | `cache_n` = previous prompt end, 4.5 to 5.7 s each | same |
| change one line inside turn 3 | `cache_n` 9, `prompt_n` 16270, 17.9 s | `cache_n` 7570, `prompt_n` 8709, 10.9 s |
| change one line inside turn 1 | `cache_n` 9, 17.9 s | `cache_n` 9, 18.1 s |

A single 16.7K-token prompt re-sent with one changed line at token 500, 8400, or 15600 re-prefills from zero under both settings (18.4 s), because a single prefill writes one checkpoint at its end. Changing only the user message re-prefills the final 512-token ubatch (`prompt_n` 517, 1.4 s). The default `--cache-ram 8192` restored an evicted 16.7K state once (`cache_n` 16694, 1.2 s) and not after three intervening prompts, so it holds two or three states of that size; it is left at the default because the host's page cache is holding the 16 GB model file.

Consequences for the briefs: every byte that moves ahead of the conversation costs the whole prefill on this model (brief 04), a working-set eviction rolls back to the nearest earlier turn-end checkpoint (brief 03 and the eviction policies), a pure append is free (brief 05), and a foreign request on the same endpoint evicts the slot but the state may come back from RAM (briefs 06 and 07).

On a one-slot server a pre-warm that will not be used is not free.
