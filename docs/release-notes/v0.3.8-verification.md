### Method

Two independent passes per file, then a third by hand.

1. **Classify.** One agent per differing file read `diff -u <(git show v0.3.8:$f) $worktree/$f`
   and classified every hunk. A residue call was only accepted if the agent located the
   equivalent on `v0.3.8` and named where it lives; an unlocated equivalent was to be
   downgraded to ambiguous.
2. **Salvage hunt.** A second agent per file, prompted adversarially and told the worktree was
   about to be deleted permanently, tried to prove the first pass wrong. The bias was made
   explicit and asymmetric: a wrong residue call destroys work, a wrong unmerged call costs
   only a redundant commit, so the instruction was to default to keeping when uncertain.
3. **Hand check.** The agents agreed unanimously, which is uniform enough to be suspicious, so
   the result was cross-checked mechanically. `git diff v0.3.8 -- <files>` per worktree gives
   the content that exists in a worktree and nowhere on `v0.3.8`: **160 lines total**
   (25 / 44 / 3 / 88). That is small enough to read in full, and it was read in full.

### Two things found during assembly

**The 0.3.8 changelog had no `### Added` section at all.** The release documented its four
fixes and the trust and scope work, but the extension resource surface, a user-visible feature
this release ships, appeared nowhere. Step 15 of the release-cut checklist requires every
user-visible behavior change under `### Added`. Written as `290a1235`. **No tracking issue
exists for the extension-resources work**, so those two entries carry no issue reference, which
is the only such pair in the section. That is a gap for the operator to close or accept.

**A defect found by the live consumer of the new extension surface, filed as #240 and fixed.**
A sibling session working against the namespaced extension prompts found that clio stripped the
quote characters around a title when expanding slash-command arguments. Investigating it showed
the mechanism is wider than quotes:

```js
// @earendil-works/pi-agent-core
parseCommandArgs()  // shell tokenizer: strips ' and ", splits on space and tab
substituteArgs()    // $ARGUMENTS = args.join(" ")
```

Every slash command in the product silently lost, from the operator's own prose, both quote
characters, every tab, and every run of more than one space including indentation. `main` and
`v0.3.8` carried the identical call, so **this is pre-existing and not a 0.3.8 regression**. It
was landed on 0.3.8 anyway, on the operator's explicit decision, because 0.3.8 is the release
that ships the namespaced prompt surface and its first real consumer hit the defect
immediately; shipping a new surface with silent payload corruption on it is shipping a broken
feature.

The fix splits semantics: `$ARGUMENTS` carries the exact post-command payload and is
substituted *after* the parsed placeholders, so a literal `$1` in operator prose stays literal;
`$1`..`$9`, `$@`, `${@:N}` and `${@:N:L}` keep shell-tokenized behavior. One further behavior
change rides along and is documented in `docs/prompt-envelope-and-tools.md`: only the first
whitespace character after the command name is the delimiter, so `/foo   bar` now yields
`  bar` for `$ARGUMENTS` where it previously yielded `bar`.

#### The differential that decided the release

The two FAIL rows above initially read as release-blocking. They are not, and one controlled

#### D1, for v0.3.9

Expansion is always exact. When the submit pipeline writes a **second** queued or echo turn,
that second turn is trimmed of leading and trailing payload whitespace and becomes the
model-facing one. In a fresh single-turn session only one row is written and it is exact,
which is why the differential is clean.

the byte-for-byte contract unconditionally, and the queued path does not honour it. That is a
documentation-versus-behavior mismatch on a path that is strictly better than 0.3.7, not a
regression. It should be filed against v0.3.9.
