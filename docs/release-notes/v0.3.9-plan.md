# v0.3.9 plan

Eighteen open issues, grouped into five themes and sequenced by dependency. No new tickets were filed to build this plan; it organizes what exists.

The milestone inherited a single theme from the v0.3.8 cut ("the behavioral evaluation track"). That is still in it, as theme E, but it is no longer the whole of it: the v0.3.8 release test added four issues, and two items moved off the v0.3.8 milestone when it was trimmed to the four release blockers.

## What moved off v0.3.8, and why

| Issue | Reason |
| --- | --- |
| #163 typed-intent migration and fail-closed refusal rules | A feature, not a fix. v0.3.8 became a four-fix patch release once the release test found a blocker; a migration-and-refusal design does not belong in it. |
| #222 close the v0.3.7 release-test residue with live assertions | Not done and not attempted. The v0.3.8 release test exercised v0.3.8 features; the seven v0.3.7 residue rows in #222 (`/oracle` mid-stream, the `/handoff` dropped-path block and its `$EDITOR` path, fleet `proposals: true`, loop `check: {kind: gate}`, `--rounds 2`, and a `DEV_COMMANDS` help test) are untouched. |

## Themes

### A — Finish the trust projection (#237, #234)

v0.3.8 closes the two defects that made the projection contradict itself (#233, #238). What it does not close is parity: surfaces that render the canonical projection and still disagree, or do not render it at all.

- **#237** — the bundle projects `completionEvidence: not_applicable` where dispatch, monitor and eval project `absent`; `findings.md` carries no verdict at all; the Alt+W board and receipt view cannot express the tier in text. The bundle disagreement is the substantive half: it composes finish-contract input the receipt-derived surfaces do not, so one of the two is not canonical and the release does not say which.
- **#234** — `targets --probe` truncates the degraded reason at every ordinary width. Small, self-contained, unrelated to the rest of the theme except that it is the same class of defect: the right information exists and the surface loses it.

Sequence #237 first. #234 is a good warm-up or filler task and blocks nothing.

### B — Dispatch correctness (#231, #236, #198, #163)

The v0.3.8 release test proved the write boundary and the fleet assignment row behave correctly under the conditions it tested. These are the conditions it did not reach.

- **#231** — no fleet step after the first can be retried. The most serious of the four: it means a transient failure anywhere past step 1 ends the fleet.
- **#236** — a downgraded write record never names the tool that downgraded it. The fallback itself is correct and verified; the gap is that an operator cannot tell a run that puts their concurrent work at risk from one that does not, either before or after the fact.
- **#198** — worker heartbeat age on a monotonic clock. Deferred twice; small and well understood.
- **#163** — typed-intent migration and fail-closed refusal rules. The design question v0.3.8 left open once typed scope became authoritative. Depends on nothing here, but it is the one that will produce the most argument, so it wants to start early rather than late.

Do #231 first. #236 pairs naturally with theme A, since both are about a surface saying what it actually knows.

### C — Context and memory economics (#227, #229, #226)

Three issues that share a root: Clio spends resources without an accurate account of what it spent.

- **#227** — context accounting never reconciles against provider counts, so compaction does not fire. This is the load-bearing one; the other two are cheaper.
- **#229** — proactive memory spends tokens invisibly and its durable store is never written.
- **#226** — the trace store has no retention and reached 94MB in 14 days.

#227 first; it is the one with a user-visible failure mode.

### D — Interactive surface (#228, #224, #223)

- **#228** — `ask_user` discards free-text answers and keeps only the option label. A silent data loss on a path the operator uses to answer a direct question.
- **#224** — the unreduced input wedge after `/share`. Carried from the v0.3.7 report, where two of three wedges were reduced and this one was not. It needs diagnosis before it can be scheduled, so treat the ticket as an investigation, not a fix.
- **#223** — `/handoff` is effectively cloud-only, because the extraction round asks for a schema in prose and binds nothing. The fix is the same shape as the `council-ballot` override that made `/council` work on local targets in v0.3.8, which is a useful precedent to follow rather than re-derive.

### E — Behavioral evaluation (#156, #160, #161, #164)

The track this milestone was originally created for. It is strictly sequenced and nothing else depends on it:

**#156** (versioned scenario and verdict schema) → **#160** (public regression corpus for built-in agents) → **#161** (multi-metric comparisons and variance gates) → **#164** (bind results to execution envelopes and release reporting).

Starting anywhere but #156 will produce work that has to be redone.

### F — Trust the tests (#232, #222)

Both of these are about the suite's ability to detect the defects the last two release tests found by hand.

- **#232** — the dispatch test stub serves a researcher that does not exist, and it hid four defects. **This should be first work in the milestone.** Every other theme's tests run through a harness that is currently able to pass while the real path is broken, which is precisely how #230, #221 and the two write-boundary defects survived a 4,900-test suite.
- **#222** — the v0.3.7 residue, seven rows needing live assertions rather than scripted workers. Same root cause as #232 and best done after it.

## Suggested order

| Wave | Issues | Rationale |
| --- | --- | --- |
| 1 | #232, #231, #227 | Fix the harness that hides defects, the fleet retry gap, and the context accounting that breaks compaction. The three highest-consequence items, all independent of each other. |
| 2 | #237, #236, #234, #228 | The reporting-honesty cluster. #237 and #236 are one conversation; #234 and #228 are small and independent. |
| 3 | #156 → #160 → #161 → #164 | The eval track, strictly in order, in parallel with wave 2 if there is capacity. It touches almost nothing the other themes touch. |
| 4 | #222, #229, #226, #198, #223, #224 | Live assertions once the harness is trustworthy, plus the remaining economics and interactive items. #224 begins as an investigation. |
| — | #163 | Design work, startable at any point, but it wants a decision before it wants code. |

## What this plan does not decide

- Whether #237's bundle disagreement is fixed by making the bundle match the receipt-derived surfaces or the reverse. That is a real design question about what "completion evidence" means when a finish contract exists, and it should be answered in the issue before code is written.
- Whether #163 is a v0.3.9 feature or the seed of a v0.4.0. It is the largest item on the milestone by a wide margin.
- Scope for the `#41` sidecar question mode, which is the only open issue on no milestone at all.
