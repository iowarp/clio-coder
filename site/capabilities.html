A coding agent.
A complete working loop.

Read a repository, make a focused change, run its checks, and delegate an independent review. Clio brings these steps into one inspectable runtime.

Built around your
verification workflow.

Use your project’s existing tests and scientific acceptance criteria.

Repository tools
Read, search, edit, and run commands through typed tools. Tool calls pass through a shared admission and safety policy.
Declared verification
The verify tool supports pytest, unittest, Cargo, Go, CMake presets, Make, just, and scripts already used by CI. It can compare numerical results and apply performance budgets.
Scientific infrastructure
Connect configured MCP servers through one gateway. Slurm job workflows use the clio-kit MCP server to submit, poll, cancel, and fetch job output.
Research procedures
Reusable skills cover scientific debugging, modernization, literature cards, and experiment protocols. The Materio plugin bundles a materials-research workflow.

Explicit rules
for real tool calls.

The prompt explains policy. The runtime applies it at execution time.

Operator-controlled autonomy
default admits workspace reads, edits, and recognized checks, while asking before unfamiliar commands, outward actions, and larger dispatches. yolo removes ordinary approval stops; hard blocks, protected paths, and damage-control rules still apply.
Protected paths
Credential paths such as .env, ~/.ssh/, and private keys are protected from tool reads and writes. Paths and symlinks are checked before execution.
Damage control
Shell commands are parsed and scanned for destructive operations, including recursive deletes, force pushes, shell chains, and substitutions.
Trusted project policy
A project .clio-coder/safety.yaml takes effect after the operator approves its exact bytes with clio-coder config trust safety.
Worker limits
Dispatched workers run at default, even when the main session uses yolo. A read-only task is a dispatch restriction, not another autonomy level.

Commands run with your user permissions. Clio’s tool policy is not an operating-system sandbox. Hooks and external agents have their own execution boundaries.

Small assignments.
Coordinated workflows.

A worker gets a role, model, tool ceiling, budget, and expected result. A fleet combines workers into a repeatable workflow.

Focused roles
Use architect, coder, debugger, documenter, git-master, tester, verifier, and wiki-writer recipes.
Capability ceilings
Read-only, verification, artifact-write, and workspace-edit define the maximum mutation boundary for a task.
Workflow topologies
Parallel, sequential, pipeline, review, compete, council, and fleet arrangements. Shipped contracts include build-test, build-review, and sdlc.
Independent host checks
Checks declared in a dispatch run on the host after a worker finishes, separately from the worker’s report.
Worktrees and write leases
A task can use its own Git worktree. A checkout-writer lease prevents multiple writers from using the same checkout concurrently.
Across SSH nodes
The worker protocol can run over SSH. Remote nodes must see the project at the same absolute path; localhost refers to that node’s model server. 
/run verifier Review the current diff and run the relevant existing checks. Do not edit files.

A large project.
A recoverable conversation.

Control what enters the model’s context while retaining the underlying session record.

Project handbook
Version your build commands, conventions, and validation rules in CLIO-CODER.md. clio-coder context init drafts the handbook and builds the code index.
Code index
A Tree-sitter index helps navigate large code trees. Parsing stays outside the interactive input loop.
Working set and recall
Eviction removes content from the next model view without deleting the ledger or transcript. Stable markers support prefix-cache reuse; /context recall can restore an observation.
Session continuity
Use /tree, /fork, and /resume to branch or recover a conversation. /export writes HTML; /export notes.md writes Markdown.
Context continuity guide →

Keep the record
behind the result.

Inspect changes and observed checks after a run, including what remains unknown.

Sealed run records
Completed runs produce immutable receipts with integrity checks, tool activity, token use, validation grounding, and outcome.
Separate trust states
Artifact integrity, validation grounding, independent review, context provenance, and completion evidence are distinct. Unknown, absent, and not applicable remain explicit states.
Unverified changes stay visible
After a file-changing turn, the finish contract looks for validation evidence or a limitation record. Without either, the model is instructed to report the change as unverified.
Trace and memory
A rebuildable SQLite trace mirrors the ledger. Memory records are approved and linked to evidence; rules-only memory is enabled by default, while model-assisted memory is opt-in. 
clio-coder evidence list
clio-coder evidence inspect <evidenceId>

Recorded checks establish observations, not scientific truth. Validate against your own reference data and acceptance criteria.

Current product status.

Experimental v0.5.6. The terminal is the primary interface.

GUI alpha
The browser application is opt-in and still developing. Terminal and GUI coverage differ.
Platform support
Linux and macOS are the primary platforms. Windows support is best effort.
Deferred work
The high-authority self-edit gate is designed but not enforced. Container and cloud worker transports are deferred.
Practical boundaries
Clio does not provide an OS sandbox, promise GUI parity, or establish scientific correctness from a passing command.
