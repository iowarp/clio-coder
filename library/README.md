# Clio Coder Library

The Clio Coder library is the canonical home of shareable packages, contributor entry points, and the generated distribution index.

## Package Kinds

The library organizes shareable packages by kind into dedicated directories:

| Kind | Directory | What an author shares | How it is used |
| --- | --- | --- | --- |
| **Skill** | `library/skills/` | A procedure and supporting knowledge for the agent | `/skill <skill-name>` |
| **Agent** | `library/agents/` | A worker recipe: role, tools, budget, and result contract | `/run <agent-id> <task>` or dispatch |
| **Prompt** | `library/prompts/` | Reusable task text and parameterized instructions | `/<derived-prompt-name> [arguments]` |
| **Fleet** | `library/fleets/` | An executable multi-agent coordination recipe | `/fleet run <name>` or preview |
| **Plugin** | `library/plugins/` | A cohesive bundle of resources released together | Inspect contents, invoke member recipes |

## Browsing and Managing Packages

```bash
# Discover packages in the catalog
clio-coder library list
clio-coder library search <query>

# Install packages
clio-coder library install skill:<name> --project
clio-coder library install plugin:materio --project

# Inspect installed packages
clio-coder library skills --all --json

# Read every discovered recipe with its owner, origin and invocation
clio-coder library recipes --json
clio-coder library recipes <query> --kind agent
```

`library recipes` reads the same bounded, body-free inventory Clio reads through `context(scope="library")`, so the operator and the model agree about which recipes exist, who owns them, where they came from and how each one is actually invoked. Both are reads: installation, removal and activation stay operator actions through `library install` and `/library`, and `/skill <name>` stays the way a skill is activated.

In an interactive session, `/library` opens the recipe browser.

## Using These Packages From Another Agent

The same sources are usable by Claude Code and Codex with no converted copy and no duplicated recipe body.

```bash
# Claude Code: the repository is a standard marketplace
claude plugin marketplace add iowarp/clio-coder
claude plugin install tdd@clio-coder

# Codex: .agents/skills already links the canonical trees, so a session
# started in a clone sees all 39 skills. For every repository:
ln -s "$PWD/library/skills" ~/.agents/skills/clio-coder
ln -s "$PWD/library/plugins/materio/skills" ~/.agents/skills/materio
```

`.claude-plugin/marketplace.json` is generated by `pnpm run library:pin` from the pinned packages in `registry.yaml` and verified by `pnpm run library:check`. It is never edited by hand.

A package is published there only when a peer host would load a real skill surface from it and nothing it would default-scan into a native component. Agent-, prompt- and fleet-only packages, and packages that keep Clio recipes in a top-level `agents/` directory, stay valid first-class library packages with no peer-host projection; `library:pin` prints which ones and why. See [coding agent interoperability](../docs/guide/interop.md) for what each host actually loads.

## Authoring Templates

Working, valid authoring templates for all five package kinds live in `library/_authoring/templates/`:

- `library/_authoring/templates/skill/`: Single skill package with house metadata, triggers, and evals.
- `library/_authoring/templates/agent/`: Standalone agent recipe with strict v1 format, custom audience, and `skills: []`.
- `library/_authoring/templates/prompt/`: Reusable prompt with path-derived invocation and argument placeholders.
- `library/_authoring/templates/fleet/`: Multi-agent coordination contract with a valid DAG and documented prerequisites.
- `library/_authoring/templates/plugin/`: Composite bundle demonstrating an agent binding a contained skill, prompts, and assets.

Templates are authoring reference models; they live outside the five catalog kind roots and never enter `library/registry.yaml`.

## Contributing Packages

Every native installable package carries a portable `plugin.json` manifest.
The optional `extensions["ai.iowarp.clio"]` metadata declares a Clio-specific
kind, resource paths and components; conventional plugin packages can expose
`skills/` without it. The key is metadata inside the interoperable manifest,
and does not name a marketplace service or require a directory. Supported
foreign plugin manifests enter through the separate reviewed import route.

1. **Choose package kind**: Decide whether your contribution is a single-kind package (`skill`, `agent`, `prompt`, `fleet`) exposing exactly one public recipe, or a composite `plugin` bundle combining multiple resources.
2. **Copy authoring template**: Copy from `library/_authoring/templates/<kind>/` into your authoring tree.
3. **Author resources**:
   - Single-kind packages expose exactly one public resource file under their resource root (`skills`, `agents`, `prompts`, or `fleets`).
   - Place `README.md` at the package root, outside the resource root, so it is not discovered as a second recipe.
   - Packages may carry explicitly invoked scripts (e.g. for offline evaluation or verification). Runtime tools and session hooks belong to the separate harness extension lifecycle.
4. **Validate**:
   ```bash
   clio-coder library validate <package-path> --json
   ```
   Validates manifest schema, resource payloads, package reference markers, and loader compatibility in a read-only pass.
5. **Pin and check**:
   ```bash
   pnpm run library:pin   # regenerates full-tree pins in library/registry.yaml
   pnpm run library:check # verifies all package bytes against library/registry.yaml
   ```
   For curated skills under `library/skills/`, maintainers also run:
   ```bash
   pnpm run skills:pin    # updates normalized skill-body provenance in library/skills/registry.yaml
   pnpm run skills:check  # verifies skill provenance records
   ```
   *Full-tree pins* cover every distributed byte for runtime package integrity; *normalized skill hashes* record advisory provenance for audited instructions.
6. **Try in isolated project**:
   ```bash
   clio-coder library register <package-path> --project
   clio-coder library install <kind>:<name> --project
   ```
7. **Submit a focused fork PR**: Push to your fork and submit a PR against `main`.

Built-in agent recipes and baseline fleets remain product-owned under `src/domains/agents/builtins/` and `src/domains/agents/fleets/`.
