# Clio Coder Library

The Clio Coder library is the canonical home of shareable packages, contributor entry points, and the generated distribution index.

## Package Kinds

The library organizes shareable packages by kind into dedicated directories:

| Kind | Directory | What an author shares | How it is used |
| --- | --- | --- | --- |
| **Skill** | `library/skills/` | A procedure and supporting knowledge for the agent | `/skill <skill-name>` |
| **Agent** | `library/agents/` | A worker definition: role, tools, budget, and result contract | `/run <agent-id> <task>` or dispatch |
| **Prompt** | `library/prompts/` | Reusable task text and parameterized instructions | `/<derived-prompt-name> [arguments]` |
| **Playbook** | `library/playbooks/` | An executable multi-agent coordination plan the fleet runs | `/fleet run <playbook>` or preview |
| **Plugin** | `library/plugins/` | Content released together; it never runs code inside Clio | Inspect contents, invoke member components |
| **Extension** | `library/extensions/` | A standalone Clio runtime package | `/ext:<id>:<command>` or `clio-coder extensions run <id> <command>` |

## Browsing and Managing Packages

```bash
# Discover packages in the catalog
clio-coder library list
clio-coder library search <query>

# Install packages
clio-coder library install skill:<name> --project
clio-coder library install plugin:materio --project
clio-coder library install extension:local-status --user

# Inspect installed packages
clio-coder library skills --all --json

# Read every discovered component with its owner, origin and invocation
clio-coder library components --json
clio-coder library components <query> --kind agent
```

`library components` reads the same bounded, body-free inventory Clio reads through `context(scope="library")`, so the operator and the model agree about which components exist, who owns them, where they came from and how each one is actually invoked. Both are reads: installation, removal and activation stay operator actions through `library install` and `/library`, and `/skill <name>` stays the way a skill is activated.

In an interactive session, `/library` opens the Library browser.

## Using These Packages From Another Agent

The same sources are usable by Claude Code and Codex with no converted copy and no duplicated component body.

```bash
# Claude Code: the repository is a standard marketplace
claude plugin marketplace add iowarp/clio-coder
claude plugin install tdd@clio-coder

# Codex: .agents/skills already links the canonical trees, so a session
# started in a clone sees all 39 skills. For every repository:
ln -s "$PWD/library/skills" ~/.agents/skills/clio-coder
ln -s "$PWD/library/plugins/materio/skills" ~/.agents/skills/materio
```

`.claude-plugin/marketplace.json` is generated by `pnpm run library:pin` from the pinned packages in `registry.yaml` and verified by `pnpm run library:check`. It is never edited by hand.

A package is published there only when a peer host would load a real skill surface from it and nothing it would default-scan into a native component. Agent-, prompt- and playbook-only packages, and packages that keep Clio agents in a top-level `agents/` directory, stay valid first-class library packages with no peer-host projection; `library:pin` prints which ones and why. See [coding agent interoperability](../docs/guide/interop.md) for what each host actually loads.

## Authoring Templates

Working, valid authoring templates for the five plugin-backed package kinds live in `library/_authoring/templates/`:

- `library/_authoring/templates/skill/`: Single skill package with house metadata and triggers.
- `library/_authoring/templates/agent/`: Standalone agent with strict v1 format, custom audience, and `skills: []`.
- `library/_authoring/templates/prompt/`: Reusable prompt with path-derived invocation and argument placeholders.
- `library/_authoring/templates/playbook/`: Multi-agent coordination playbook with a valid DAG and documented prerequisites.
- `library/_authoring/templates/plugin/`: Plugin demonstrating an agent binding a contained skill, prompts, and assets.

Templates are authoring reference models; they live outside the five catalog kind roots and never enter `library/registry.yaml`.

## Contributing Packages

Plugin-backed packages carry a portable `plugin.json` manifest. Standalone
extensions carry `clio-coder-extension.yaml` and install through the extension
writer when selected as `kind: extension` in the library.
The optional `extensions["ai.iowarp.clio"]` metadata declares a Clio-specific
kind, resource paths and components; conventional plugin packages can expose
`skills/` without it. The key is metadata inside the interoperable manifest,
and does not name a marketplace service or require a directory. Supported
foreign plugin manifests enter through the separate reviewed import route.

A plugin and an extension are separate packages. The plugin is content: a
portable `plugin.json` that installs without running code inside Clio. The
extension is Clio code: a `clio-coder-extension.yaml` with `runtime.api: 2`, its
own digest, state and envelope consent. An extension may name the one plugin it
serves with top-level `plugin: <name>`; that link alone makes `replaces: prompt`
legal for the plugin's own `/<plugin>:<command>` prompt, and the takeover applies
only while the plugin is installed and enabled. The plugin keeps a working
fallback when its extension is absent. An extension root never holds `plugin.json`.

1. **Choose package kind**: Decide whether your contribution is a single-kind package (`skill`, `agent`, `prompt`, `playbook`) exposing exactly one public component, or a composite `plugin` combining multiple components.
2. **Copy authoring template**: Copy from `library/_authoring/templates/<kind>/` into your authoring tree.
3. **Author resources**:
   - Single-kind packages expose exactly one public resource file under their resource root (`skills`, `agents`, `prompts`, or `playbooks`).
   - Place `README.md` at the package root, outside the resource root, so it is not discovered as a second component.
   - Packages may carry explicitly invoked scripts (e.g. for offline evaluation or verification). Runtime tools and session hooks belong to an extension package.
4. **Validate**:
   ```bash
   clio-coder library validate <package-path> --json
   ```
   Validates manifest schema, resource payloads, package reference markers, and loader compatibility in a read-only pass.
5. **Pin and check**:
   ```bash
   pnpm run library:pin   # regenerates full-tree pins in library/registry.yaml
   pnpm run library:check # verifies all package bytes against library/registry.yaml
   ```
   For curated skills under `library/skills/`, maintainers also run:
   ```bash
   pnpm run skills:pin    # updates normalized skill-body provenance in library/skills/registry.yaml
   pnpm run skills:check  # verifies skill provenance records
   ```
   *Full-tree pins* cover every distributed byte for runtime package integrity; *normalized skill hashes* record advisory provenance for audited instructions.
6. **Try in isolated project**:
   ```bash
   clio-coder library register <package-path> --project
   clio-coder library install <kind>:<name> --project
   ```
7. **Submit a focused fork PR**: Push to your fork and submit a PR against `main`.

Built-in agents and baseline playbooks remain product-owned under `src/domains/agents/builtins/` and `src/domains/agents/playbooks/`.
